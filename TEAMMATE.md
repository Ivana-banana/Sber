# TEAMMATE.md — что нельзя сделать на этой машине

Дата: 26.08.2026. Файл для передачи участнику с другим железом или другим доступом.
Каждый пункт — законченная задача с командой и признаком готовности, а не «посмотри».
Доска текущей работы остаётся в `HANDOFF.md`; здесь только то, что упирается
физически в эту машину.

Железо этой машины, чтобы не проверять заново:

| | |
|---|---|
| CPU | Intel i5-1155G7, 8 потоков, есть AVX2 и AVX512 |
| GPU | нет дискретной; `nvidia-smi` отсутствует, только Iris Xe |
| RAM хоста | 8 362 713 088 Б (7.8 GiB) |
| RAM внутри WSL2 `ozon` | 5 GiB — это и есть потолок для инференса |
| Диск | 936 GiB свободно в WSL2 |
| Сеть | есть, но нестабильная: длинные HTTPS-загрузки рвутся с `SSL routines::unexpected eof`, докачка по `-C -` в цикле обязательна |
| Docker | работает внутри WSL2, целевой образ загружен по digest |

## 1. Baseline на рекомендованной модели (7B). Нужна машина с GPU или ≥16 GiB RAM

**Почему не здесь.** Qwen2.5-Coder-7B-Instruct Q4_K_M — 4 683 073 536 Б весов
(размер сверен с HF API). При 5 GiB, доступных WSL2, на KV-cache при `ctx-size 4096`
и рабочие буферы не остаётся ничего. Разгон `.wslconfig` упирается в 7.8 GiB хоста.

**Что уже сделано здесь, повторять не нужно.** `llama.cpp` собран ровно на том
коммите, который рекомендует отчёт M22, в варианте CPU:

```sh
git clone https://github.com/ggml-org/llama.cpp.git && cd llama.cpp
git checkout c1d0e7a004015f23bc0233470b747b596f29b264
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DLLAMA_CURL=ON
cmake --build build --config Release --target llama-server -j6
./build/bin/llama-server --version
#   version: 0.3.0-dev (build 10621, commit c1d0e7a00)
#   built with GNU 11.4.0 for Linux x86_64
```

Понадобился только `apt-get install build-essential cmake git curl libcurl4-openssl-dev`.
Для GPU добавить `-DGGML_CUDA=ON` и сначала убедиться, что `nvcc --version` работает.
Все флаги запуска сверены с `tools/server/README.md` этого же коммита — команда и
разбор в `docs/research/local-model-baseline.md` §3 и `verdict-local-model-baseline.md` §1.

**Задача.**

1. Поднять сервер:

   ```sh
   ./build/bin/llama-server \
     --hf-repo Qwen/Qwen2.5-Coder-7B-Instruct-GGUF:Q4_K_M \
     --jinja --ctx-size 4096 --n-gpu-layers all --flash-attn auto \
     --temp 0 --alias qwen2.5-coder-7b-q4km --host 127.0.0.1 --port 8080
   ```

   Осторожно: в этом репозитории Q4_K_M лежит и одним файлом, и двумя шардами
   (`…-00001-of-00002.gguf`). Если сработает выбор шарда, скачать одиночный файл
   руками и передать `-m`.

2. Прогнать `python scripts/probe_endpoint.py` и записать, на какой ступени
   лестницы оказался прогон.
3. Прогнать 18 фикстур из `local_task_extra/tasks/` через настоящий `run.sh`.
4. Записать карточку E010 в `docs/experiments.md` **двумя раздельными метриками** —
   protocol pass rate по каждой ступени и semantic tool correctness. Не усреднять:
   grammar на стороне сервера поднимает первую, почти не трогая вторую.

**Готово, когда** в `docs/experiments.md` есть карточка с числом решённых задач,
input/output/total токенами и wall time, а в `HANDOFF.md` снята строка про baseline.

**Разблокирует:** E001, абляции токен-экономии A001–A005, прогон 15 фикстур
инъекций, перевод prompt на английский (там нужна абляция), всю волну 3 промптов.

## 2. Вопрос организаторам про способ распаковки архива. Нужен человек

Строка висит в `HANDOFF.md` с 25.08 и остаётся **блокером выпуска**.

Факты, которые уже проверены внутри целевого образа (E003): `unzip` сохраняет
исполняемый бит и `./run.sh` из чистого каталога даёт `0` без всякого `chmod`;
`python3 -m zipfile -e` распаковывает как `-rw-r--r--`, и тогда `./run.sh` даёт
`126` на **всех** задачах. Упаковкой это не лечится — режим и Unix host-байт в
архиве уже правильные.

**Задача.** Спросить организаторов, чем распаковывается присланный `.zip`, либо
получить наблюдение реального runner'а. Если ответ — `python3 -m zipfile`, нужен
запасной план (например, `run.sh` как sh-обёртка, которую вызывают через `sh`,
а не `./`).

## 3. Перепроверка таблицы vLLM. Нужна машина, где vLLM вообще ставится

Отчёт M22 зафиксировал vLLM на `0.19.1` (18.04.2026), тогда как текущий релиз —
`0.28.0` (26.08.2026). Разница в девять релизов у проекта, который чаще всего
меняет именно tool-parser и `response_format`.

**Задача.** На машине с GPU поднять vLLM той версии, которую реально ставят, и
проверить три вещи: работает ли automatic tool choice без `--enable-auto-tool-choice`,
ограничивает ли `json_schema` генерацию на самом деле, и остаётся ли `strict: true`
no-op. Результат — правка §«Сравнение серверов» в
`docs/research/verdict-local-model-baseline.md`.

Установка vLLM здесь не пробовалась: без GPU это CPU-backend, который сам по себе
ничего не скажет о tool parser на GPU-пути.

## 4. Прогон 15 фикстур prompt injection. Ждёт п. 1

Фикстуры лежат в `tests/fixtures/prompt-injection/`, критерий приёмки —
`check_no_injection.py --root .` с пустым списком маркеров.

**Почему не здесь.** Технически можно будет запустить, как только приедет модель,

близка к нулю, и «инъекция не сработала» будет означать «модель вообще ничего не
сделала». Нужна та же модель, на которой снят baseline из п. 1.

здесь, но по другой причине.

## 5. Landlock на ядре, которое реально считает. Нужен доступ к среде оценки

`scripts/probe_landlock.py` написан и отработал: внутри целевого образа под штатным
seccomp-профилем Docker он даёт

```
kernel:  Linux 6.6.87.2-microsoft-standard-WSL2 (x86_64)
no_new_privs: yes (set by this process)
landlock ABI: 3 (+ truncate)
verdict: YES -- a path allow-list is enforceable from inside this process
```

**И это ничего не доказывает про оценку.** У контейнера нет своего ядра: прогон
внутри образа и прогон голым WSL2 напечатали одну и ту же строку `kernel:`. То есть
измерено ядро этого ноутбука. Исходная формулировка задачи в `HANDOFF.md`
(«поддерживает ли ядро образа Landlock») была неверной по существу и исправлена.

**Задача.** Прогнать тот же скрипт там, где будет считаться сабмишен, — либо
получить от организаторов версию ядра и факт `CONFIG_SECURITY_LANDLOCK=y`. Скрипт
read-only: он не создаёт ruleset и ничего не ограничивает.

**Разблокирует** первое из двух условий `TBD` про ограничение `run_shell`
(`docs/decisions.md`). Второе — marker-rate на 15 фикстурах — упирается в п. 1.

## 6. Решение про `.venv` в брифинге. Нужен baseline, а не железо

Наблюдение, снятое внутри целевого образа 26.08 (протокол —
`docs/research/image-substitutions.md` §4): `/app/.venv/` лежит внутри рабочего
каталога задачи, и обход `_walk` тратит на него **10 из 30** записей дерева. На
разобранном примере из одиннадцати перечисленных записей десять принадлежали venv,
а единственный файл улик оказался последним.

Напрашивается пропуск `.venv` в `agent/preflight.py::_walk`. Изменение
однострочное, но меняет поведение на **всех** задачах, а измерить его без baseline
нечем — поэтому оно намеренно не сделано, а записано.

**Задача.** После п. 1 прогнать 18 фикстур с пропуском и без, сравнить solved count
и токены, принять или отклонить. Один фактор за прогон.

## 7. Мелочь, которую стоит знать заранее

- Загрузка весов с Hugging Face на этой машине рвётся: `curl: (35)
  error:0A000126:SSL routines::unexpected eof while reading`, дважды на разных
  файлах. Лечится циклом `curl -C - --retry 5 --max-time 600` до достижения
  ожидаемого размера. Если у вас то же самое — это сеть, а не HF.
- `nohup … &` внутри `wsl.exe -e bash -lc` не переживает выход из сессии: фоновая
  задача умирает вместе с ней. Длинные загрузки запускать как задачу процесса,
  который живёт, а не через `nohup` в одноразовом shell.
- В WSL2 не оставляйте каталог `/app`: `resolve_workspace` подхватывает его как
  fallback, и три теста в `tests/test_main.py` начинают падать на ровном месте.
  Наступил на это 26.08 после прогона cookbook'а.
