# GIT.md — правила ведения Git

Цель: `main` в любой момент представляет воспроизводимый кандидат, а для каждой
контрольной точки можно однозначно восстановить код, архив и измеренные результаты.

Правило: **закончил одно логическое действие — проверь и закоммить**.

## Перед началом работы

```bash
git status -sb
git fetch --all --prune
git status -sb
```

Если есть чужие незакоммиченные изменения или ветка отстаёт, не перетирать их.
Сначала согласовать границы в `HANDOFF.md` или с владельцем задачи. `pull` не
использовать как автоматический способ «починить всё» посреди незавершённой работы.

Эту проверку повторяем не только утром: перед общим контрактом, после любого
долгого теста/перерыва и непосредственно перед коммитом, merge или push. После
`fetch` смотреть, что появилось с обеих сторон:

```bash
git log --oneline HEAD..origin/main
git log --oneline origin/main..HEAD
```

Если у тиммейта появился пересекающийся коммит, остановиться, прочитать diff и
согласовать интеграцию. Частые маленькие коммиты снижают цену такого согласования.

## Коммиты

Формат:

```text
<поток>: <что закончено>
```

| Префикс | Поток |
|---|---|
| `agent:` | основной цикл, budgets, state, завершение |
| `prompt:` | системный prompt, routing, context management |
| `tools:` | shell/file/search/patch инструменты и политики |
| `eval:` | тесты, Harbor-прогоны, метрики, анализ ошибок |
| `pack:` | `run.sh`, сборка и валидация submission |
| `infra:` | окружение, Docker, CI, зависимости, Git |
| `docs:` | планы, решения, инструкции, отчёт |
| `fix:` | локальный исправляющий коммит, если поток смешанный |

Примеры:

```text
pack: validate run.sh contract in clean container
eval: record baseline across seven public tasks
prompt: reserve final budget for verification
```

Коммит содержит один осмысленный шаг. Не смешивать prompt-эксперимент, рефакторинг
инструментов и документацию случайным образом: такой результат нельзя сравнить.

## Ветки и ревью

- `main` — запускается, тесты зелёные, нет известных регрессий относительно
  записанного baseline.
- Крупная/рискованная работа: `<поток>/<короткая-тема>`, например
  `prompt/compact-verifier` или `tools/safe-shell`.
- Мелкие безопасные изменения допустимы в `main` после локальных проверок.
- Перед merge автор обновляет ветку от актуального `main`, прогоняет заявленные
  проверки и добавляет результаты в PR/`docs/experiments.md`.
- Минимум один человек другого потока ревьюит изменения в prompt, tool policy,
  budgets, `run.sh` и сборщике submission: там единичная ошибка превращает все задачи
  в нули.
- Force-push в `main` запрещён. Общую опубликованную историю не переписывать.

## Что не коммитим

- `.env`, ключи, токены, дампы окружения с секретами;
- `.venv/`, `venv/`, `__pycache__/`, `.pytest_cache/`, `.ruff_cache/`, кэши моделей;
- временные workspace задач, контейнерные слои, большие сырые логи;
- архивы/бинарники, не нужные для воспроизведения исходников.

Собранный `submission.zip` по умолчанию является производным артефактом и не
коммитится. Для каждой отправки фиксируются builder command, размер, SHA-256 и tag.
Если команда решит хранить архив в Git, это отдельное решение в
`docs/decisions.md`; лимит соревнования 10 МБ всё равно проверяется автоматически.

## Ремоуты

Сейчас настроен только `origin`:
`https://github.com/Ivana-banana/Sber.git`.

Не выдумывать второй remote. Если организаторы выдадут отдельный командный
репозиторий, добавить его после проверки URL и записать схему синхронизации здесь.
Перед отправкой контрольной точки убедиться, что нужный commit действительно есть
на сервере:

```bash
git rev-parse HEAD
git ls-remote origin main
```

## Контрольные точки и теги

Каждую реально отправленную версию тегировать после проверки фактического архива:

```bash
git tag -a submit-2026-08-31-kt4 -m "KT4: <solved>/15, <tokens> tokens, <seconds> s, sha256 <archive>"
git push origin main --tags
```

Не ставить тег заранее. В `docs/experiments.md` рядом должны быть commit, команда
сборки, checksum, размер, модель и результат последнего полного прогона.

Промежуточные стабильные вехи:

- `v0.1-contract` — контракт `run.sh` проходит чистый smoke;
- `v0.2-baseline` — измерен полный public baseline;
- `v0.3-robust` — закрыты основные failure modes, offline package зелёный;
- `v1.0-submission` — финальный кандидат воспроизводим из чистого checkout.

## Безопасный откат

| Ситуация | Действие |
|---|---|
| Посмотреть историю | `git log --oneline --decorate --graph` |
| Посмотреть незакоммиченные изменения | `git diff` / `git diff --staged` |
| Вернуть конкретный свой файл | `git restore <path>` после проверки diff |
| Отменить опубликованный коммит | `git revert <hash>` |
| Временно посмотреть старое состояние | `git switch --detach <tag-or-hash>` |

Не применять `git reset --hard`, `git clean -fd` или массовый `git restore` в общем
workspace без явного согласования: там могут быть изменения другого участника.
