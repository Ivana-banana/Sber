# Промпт для сессии на стенде 4080: закрытый набор без переобучения

Скопировать всё ниже черты в новую сессию агента на машине со стендом (Qwen3.6-35B-A3B,
30B). Сокомандник запускает прогоны и пишет код.

---

Ты работаешь в репозитории AIRI-агента. Сначала прочитай `CLAUDE.md`, `GIT.md`,
`HANDOFF.md` и в `docs/experiments.md` карточки `AFK-4080-final-9`,
`REVIEW-afk-4080-smoke`, `REVIEW-oracle-replay`, `AB7B-local`. До сдачи около суток,
отправка одна. Ранжирование: решённые задачи из 15 закрытых → токены → время.

## 2. Главный риск — переобучение, и как его не допустить

Каждое изменение с 06.09 отбиралось по 6 публичным задачам. Extra-набор мы уже
использовали для поиска багов, так что он тоже частично «видел» агента. Поэтому три
набора с жёсткими ролями:

| Набор | Роль | Что с ним можно |
|---|---|---|
| `local_task` (6) | регресс-шлюз | ≥ 17/18 при n=3, не тюнить |
| `local_task_extra/tasks` (18) | **dev** | читать логи, искать причины, чинить |
| `local_task_holdout/` (новый, 16–20) | **holdout** | только итоговый замер, логи агента не открывать до решения о кандидате |

Правила holdout:
1. Holdout пишется **до** первого прогона агента на нём и замораживается коммитом.
   SHA этого коммита записать в карточку; после заморозки задачи не правятся, кроме
   явно сломанной проверки (исправление — отдельной карточкой с причиной).
2. Автор задач не смотрит `agent/` и логи прогонов. Если пишет агент, то свежий subagent,
   которому дают только эту спецификацию и сами публичные задачи (`local_task/*`).
3. Решение «какой коммит отправлять» принимается по holdout, а не по dev. Изменение,
   поднявшее dev, но не holdout, не принимается.
4. `scripts/check_no_task_hardcode.py` расширить именами, путями, флагами и ответами
   holdout и extra — в `agent/` их быть не должно.

## 3. Как писать holdout-задачи (аналогично публичным)

Сначала разобрать каждую публичную задачу: `instruction.md`, `task.toml`,
`environment/Dockerfile` и `entrypoint.sh`, `tests/test.sh` с проверками,
`solution/solve.sh`. Новые задачи повторяют **форму** публичных, а не их содержание.

**Общие требования к каждой задаче**
- Тот же формат Harbor: `instruction.md`, `task.toml` (лимиты как у ближайшей публичной),
  `environment/` (`FROM secureintelligent/acp:latest`, как в public, а не `python:slim`,
  как в extra), `tests/test.sh` пишет `1`/`0` в `/logs/verifier/reward.txt`,
  `solution/solve.sh`.
- Проверка бинарная и детерминированная, как в public: pytest на файл или на сервис,
  точное сравнение, парс JSON. Тесты не кладутся в образ (их доставляет харнесс после
  прогона агента).
- Три контроля на каждую задачу (скрипт в `local_task_holdout/tools/`):
  (а) `solve.sh` → reward 1; (б) ничего не делать → reward 0; (в) правдоподобный
  неверный ответ (приманка, первый хоп XFF, удалённый тест, ослабленный assert) → 0.
  Задача без трёх зелёных контролей в набор не входит.
- Оракул агента: прогнать holdout через `scripts/eval/replay/` со сценарием из
  `solve.sh`. Если идеальная модель не решает задачу, это дефект агента или задачи, и
  его надо разобрать до замеров на модели.

**Семейства и оси варьирования** (по 4–5 задач на семейство, формулировки своими словами,
не копировать фразы public):

1. **Exact-file** (как hello/bye) — 2–3 задачи: путь вне `/app` в ещё не существующем
   каталоге; содержимое с пробелом, кавычкой или юникодом; инструкция на русском;
   «без перевода строки» сказано другими словами.
2. **Code-audit FastAPI + PostgreSQL** (как find-sqli-login) — 4 задачи с тем же видом
   отчёта `findings` [title, severity, category, location, evidence, impact,
   recommendation]. Разные классы уязвимостей: IDOR на `/users/{id}`, path traversal в
   скачивании файла, command injection в диагностическом endpoint, захардкоженный секрет
   JWT или слабая проверка токена. В коде есть приманки: безопасный параметризованный
   запрос рядом с опасным, комментарий «this is vulnerable» над безопасным кодом.
   Проверка: pytest по `category`/`location` с синонимами, как в public.
3. **Code-fix FastAPI + PostgreSQL с запущенным uvicorn** (как fix-sqli-*) — 5 задач.
   `entrypoint.sh` поднимает postgres и сервис. Проверяющий, как в public, убивает
   uvicorn, поднимает заново из кода агента и гоняет регрессию и security-тесты.
   Уязвимости: SQLi в `ORDER BY`/`LIMIT` (параметризацией не лечится, нужен allowlist),
   path traversal, отсутствие проверки владельца (IDOR), command injection через
   `subprocess(shell=True)`, SSRF к внутреннему адресу. В одной задаче сервис запущен
   через `export VAR=…` в entrypoint (проверяет перезапуск C4 без окружения). В одной —
   регрессионные тесты не идемпотентны, как `test_create_tag`.
4. **Forensics key=value** (как incident-log-forensics) — 4 задачи. Несколько источников:
   access log, JSONL-аудит, auth.log, фрагмент после усечения, `.gz`-ротация. Оси: XFF
   с доверенными прокси (атакующий не первый хоп), подделанный XFF без подтверждения во
   втором источнике, вообще без прокси; таймстемпы в разных зонах, «скопировать
   verbatim»; приманка-хост с похожим поведением; ключи с другими именами.
5. **Сервис-челлендж** (CTF-подобный, в public нет, но закрытый набор может содержать) —
   2 задачи: флаг/доказательство выдаёт только сервис после обхода проверки, статическая
   строка в файлах — приманка.

Итого 17–19 задач. Время на написание — не больше 3–4 часов. Пока пишутся задачи, стенд
гоняет шаг 4.1.

## 4. План работ (по порядку, каждый шаг — коммит и карточка в `docs/experiments.md`)

4.1. **Регресс ветки на public (стенд c, n=3).**
```
git fetch --all --prune
git checkout -b eval/holdout origin/fix/review-afk-4080
git merge origin/afk/4080-20260916          # там только документы
python3 -m pytest -q
python3 scripts/build_submission.py --out build/review.zip && python3 scripts/check_submission.py build/review.zip
python3 scripts/eval/run_suite.py --tasks-root local_task --model <модель c> --base-url <url> \
  --api-key <key> --counter-container <proxy> --repeats 3 --timeout-scale 1.0 \
  --archive build/review.zip --label PUB-review --out build/eval-PUB-review
```
Шлюз: ≥ 17/18. Ниже — найти коммит-виновник откатом по одному и сообщить.

4.2. **Оракул на всех наборах.** `scripts/eval/replay/`: extra 18/18, public fix-задачи и
holdout после заморозки. Любой не-`verified` оракула — дефект агента, чинить первым.

4.3. **Dev-замер: extra ×3, кандидат-9 против ветки**, одинаковые условия. Таблица solved
по категориям, токены, время.

4.4. **Таксономия нулей dev** — основной аналитический результат. Одна строка на ноль:
`задача | повтор | stop | что на диске | почему проверка 0 | класс`. Классы: `startup`,
`budget/timeout`, `steps`, `tool-refused` (выписать команду), `wrong-workspace`,
`wrong-playbook` (см. `agent ready`/`classify` в логе), `format`,
`reasoning-wrong-answer`, `no-interaction` (ответ вычитан статически, а нужен сервис),
`false-verified`. Топ-3 класса по числу нулей.

4.5. **Исправления по топ-3 — по одному фактору.** Для каждого:
- гипотеза;
- падающий тест **без** имён, путей и ответов задач (формулировки перефразировать);
- минимальная правка;
- `python3 -m pytest -q`, `scripts/check_no_task_hardcode.py`;
- оракул не хуже;
- extra ×3 против контроля 4.3.

Принимать, если dev вырос и public ≥ 17/18. Промпт, tool policy и бюджеты — только
через ревью человеком перед `main`.

4.6. **Holdout-замер — единственное основание для выбора.** Заморозка → оракул →
кандидат-9, ветка и лучший кандидат 4.5, каждый ×3. Открывать логи holdout можно только
после того, как числа записаны в карточку. Отправляется кандидат с максимумом на holdout
при public ≥ 17/18; при равенстве — меньше токенов.

4.7. **Переносимость.** Финалиста один раз прогнать на 30B (и 7B, если есть время): резкая
регрессия относительно кандидата-9 — стоп-сигнал, модель организаторов неизвестна.

4.8. **Финал.** Собрать архив из коммита финалиста, `check_submission`, распаковать
собранный zip и прогнать smoke в `secureintelligent/acp` offline, записать SHA и размер,
тег по `GIT.md`.

## 5. Известные открытые вопросы (кандидаты для 4.5, только если их подтвердит таксономия)

- Роутер на свежих формулировках всё ещё 12/20; промахи уходят в `general`. Проверить на
  dev, стоит ли специальный playbook решённой задачи: абляция «всегда general» против
  роутера. Не добавлять слова под конкретные задачи.
- Recovery: один проход (`MAX_RECOVERY_PASSES=1`). Больше проходов — только с защитой от
  неидемпотентных тестов (например, если та же проверка уже была зелёной после последней
  правки), и только по данным.
- C4 не переносит переменные окружения сервиса (`export` в entrypoint) — holdout-задача
  из п. 3.3 это покажет.
- Code-fix по-прежнему отклоняет `python3 -c`, `sqlite3`, `pip list`: посчитать в логах,
  как часто модель в это упирается.
- Пакет L1 даёт около 1000 символов на файл; строка про XFF в forensics-playbook
  появилась после провала public incident — проверить на holdout-форензике с доверенными
  прокси.
- Модели с рассуждением: таймауты и обрывы рассуждения (L3) — смотреть `llm-unusable`.

## 6. Запреты

- Никаких имён, путей, флагов, ответов и формулировок public/extra/holdout в `agent/`.
- Не смотреть логи holdout до записи его чисел; не править holdout после заморозки.
- Один фактор на эксперимент; каждый прогон — карточка: команда, SHA архива, модель,
  стенд, solved, токены, время, таксономия нулей, путь и checksum сырого results.tsv.
- Не принимать по одному прогону (n ≥ 3). Разница в 1–2 задачи на 18 при n=1 — шум.
- Не вливать в `main` без ревью человеком; force-push запрещён; перед push —
  `git fetch --all --prune` и обе стороны расхождения; `git add` только явных путей.
- Значения `LOCAL_AGENT_MODEL`, `OPENAI_BASE_URL`, `OPENAI_API_KEY` не логировать.
