Скопировать целиком в новую сессию агента на машине со стендом (Qwen3.6-35B-A3B и 30B).

---

Ты работаешь в репозитории AIRI-агента. Прочитай `CLAUDE.md`, `GIT.md`, последние карточки
`docs/experiments.md` (AFK-4080-final-9, REVIEW-afk-4080-smoke) и `HANDOFF.md`.

## Цель сессии
Получить измеренный ответ «на каких классах задач агент проваливается и почему», а не
ещё одну эвристику под public. Никаких изменений в `agent/` до шага 4.

## Шаги (строго по порядку, каждый — коммит и карточка в `docs/experiments.md`)

1. **Регресс-страж ветки ревью на public.**
   `git fetch && git checkout -b eval/review-merge origin/fix/review-afk-4080 && git merge origin/afk/4080-20260916`
   (там только документы). `python3 -m pytest -q` — зелёный. Собрать архив
   `python3 scripts/build_submission.py --out build/review.zip`,
   `python3 scripts/check_submission.py build/review.zip`.
   Стенд c, `--tasks-root local_task`, 3 повтора. Шлюз: ≥17/18. Если ниже — разобрать
   каждый ноль по логам, найти, какой из 7 коммитов виноват (`git revert` по одному),
   сообщить, не чинить вслепую.

2. **Главный замер: extra-набор, оба кандидата, одинаковые условия.**
   Собрать образы extra (нужен интернет при сборке). Для `9a8673c` и для ветки ревью:
   ```
   python3 scripts/eval/run_suite.py --tasks-root local_task_extra/tasks \
     --model <модель стенда c> --base-url <url> --api-key <key> \
     --counter-container <proxy> --repeats 3 --timeout-scale 1.0 \
     --archive build/<cand>.zip --label EXTRA-<cand> --out build/eval-EXTRA-<cand>
   ```
   Записать solved/54, токены, время по каждой задаче и по категориям
   (audit / ctf / fix / forensics / mut).
   **Разделить extra до чтения логов:** dev = 9 задач (разбирать логи, чинить), holdout =
   9 задач (только финальный замер, логи не открывать), `mut-*` поровну. Решение о
   кандидате принимать по holdout, иначе extra переобучится так же, как public.

3. **Таксономия нулей — это основной результат сессии.**
   Для каждого нуля extra прочитать лог агента (`agent tool:` строки, `agent done`),
   `.post`/deliverable и вывод verifier. Одна строка на ноль в таблицу:
   `задача | повтор | stop | что было на диске | почему verifier поставил 0 | класс`.
   Классы: `startup`, `timeout/budget`, `steps`, `tool-refused` (политика агента
   отклонила нужную команду — выписать команду), `tool-broken`, `wrong-workspace`,
   `format` (файл есть, форма не та), `reasoning-wrong-answer`, `no-interaction`
   (ответ вычитан статически, а сервис надо было вызвать), `false-verified`
   (агент сказал verified, verifier — 0). Особое внимание `tool-refused` и
   `false-verified`: это дефекты агента, а не модели.
   Результат: таблица + топ-3 класса по числу нулей в `docs/experiments.md`.

4. **Только теперь — по одному фактору на верхний класс.** Для каждого из топ-3:
   гипотеза, воспроизводящий тест (без имён/путей/ответов конкретных задач —
   `scripts/check_no_task_hardcode.py` должен быть чистым), минимальная правка,
   прогон extra ×3 против контроля из шага 2. Принимать, только если solved на extra
   вырос и public не упал ниже 17/18. Не принимать по одному прогону.

5. **Переносимость на слабую модель.** Лучшего кандидата один раз прогнать на 7B
   (`qwen2.5-coder:7b-instruct-q4_K_M`) по public и extra. Модель организаторов
   неизвестна; регресс на 7B против E060 (5/18) — стоп-сигнал.

## Что проверять попутно (известные открытые вопросы)
- `max_recovery_passes = 1`: сколько нулей extra — `verify-failed` при запасе времени
  > 50 %. Если это заметный класс — кандидат для шага 4.
- Строка про forwarded-for в forensics-playbook подогнана под public incident. На
  extra-форензике проверить, не ухудшила ли она атрибуцию; общее правило — разбирать
  XFF справа налево, пропуская доверенные/внутренние прокси.
- Пакет L1 показывает ~1000 символов на файл: посчитать, сколько шагов уходит на
  перечитывание того же файла отдельным вызовом.

## Запреты
- Не хардкодить имена, пути, флаги и ответы public/extra.
- Один фактор на эксперимент; каждый прогон — карточка с командой, SHA архива, моделью,
  solved, токенами, временем, таксономией нулей.
- Не вливать в `main` без ревью человеком (prompt, tool policy, budgets).
- Не использовать force-push; перед push — `git fetch --all --prune` и обе стороны
  расхождения.
