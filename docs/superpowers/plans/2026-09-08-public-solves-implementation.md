# Public solves — план реализации и проверки

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Пользователь передаёт реализацию Claude; автор этого плана код не меняет. Реализация и локальные эксперименты выполняются последовательно, без повторного согласования каждого шага уже переданного плана.

**Goal:** получить новые воспроизводимые победы на публичных задачах, сохранив прежние; первый целевой рубеж — 3/6 без timeout.

**Architecture:** сохранить один tool loop. Сначала проверить, решает ли модель audit с нужным исходником, затем обеспечить автономную доставку этого исходника. После этого разделить результат ремонта и произвольную запись файла, а для forensic обеспечить исполнение расчёта по предоставленным данным. Каждый фактор испытывается отдельно, комбинация — только после понимания её составляющих.

**Tech Stack:** Python 3.12, stdlib, существующие Docker/eval tools и локальный endpoint; новых runtime dependencies нет.

**Spec:** [разбор A20260908](../../research/night-public-analysis-2026-09-08.md), [предыдущая причинная диагностика](../../research/night-public-analysis-2026-09-07.md). Читать оба, но текущую полноту N2/N3 брать из A20260908.

## Глобальные ограничения

- Пользователь сейчас заказал план; этот документ — инструкция будущей реализации, не отчёт о выполненном коде. Тестовые сценарии описаны словами по требованию «не пиши код»; исполнитель пишет воспроизводящий тест перед каждой правкой.
- Сначала `git status -sb`, полностью CLAUDE.md, затем GIT.md, PLAN.md, HANDOFF.md и docs/task.md. Чужой `deep-research-report.md` не менять. Работать в отдельном checkout/worktree; не переключать общий каталог поверх WIP.
- Интернет не использовать, зависимости агента не устанавливать. Доступ к уже настроенному локальному endpoint — часть эксперимента. Fetch/push выполнять лишь если текущие указания человека разрешают сетевую синхронизацию; при действующем запрете интернета фиксировать локальные коммиты и отсутствие синхронизации.
- Агент видит instruction и environment задачи; содержимое organizer solution, evaluator, expected answers ему не передаётся. Eval может читать и запускать checker снаружи. Никакого хардкода public names/paths/answers в submission, включая комментарии и docstrings.
- Runtime не получает task.toml, reward и привилегированное знание внешнего лимита. Не использовать `--tell-agent-budget`, увеличение timeout-scale или ручное исправление workspace для зачётных прогонов.
- Модель `qwen2.5-coder:7b-instruct-q4_K_M`, context=4096, temperature=0, controller=loop. MAX_STEPS, модель, протокол и общий budget не менять попутно. N2 не принят, N3 ещё не измерен.
- Один endpoint — один активный eval. Не запускать старую ночную очередь, не перезапускать модель посреди пары B/T. После изменения состояния стенда начинать новую пару.
- Каждая законченная задача: воспроизводящий тест → минимальная правка → targeted tests → нужный public-пилот → experiments/decision → отдельный коммит. Для экспериментальных факторов статус решения — «гипотеза» до приёмки.
- 3/6 — промежуточная цель, не потолок и не обещание. После неё продолжать по плану, сохраняя лучший измеренный архив. Не считать больше файлов, более красивый отчёт или экономию токенов приростом качества.

## Порядок и ограничение затрат

Основной маршрут: **P0 → P1 → P2 → P3 → P6**. После первого успеха P4 и P5 дают следующие public-победы. Если audit не получается, это альтернативные ветви поиска первого успеха: при доставленном коде можно пробовать P4, при двух reasoning-нулях P1 — P5. Любая новая победа возвращает к P3; перед передачей кандидата всегда выполняется P6.

| Этап | Ориентир времени, не гарантия | Результат/условие выхода |
|---|---|---|
| P0, измерения и свежий B | 45–75 минут | честная полная public-база, неперезаписываемые результаты |
| P1, assisted audit | до 30 минут, не более 2 LLM-попыток | отделено понимание кода от навигации |
| P2, автономный audit | 90–150 минут | новый audit reward либо локализованный остаточный сбой |
| P3, подтверждение | резерв 60–90 минут | полная шестёрка, повторные победы, неизменный архив |
| P4, настоящий code-fix | следующий приоритет, пилот до 90 минут | первая исправленная public-задача |
| P5, forensic | следующий приоритет, пилот до 90 минут | вычисленный и проверенный отчёт |
| P6, выпускной gate | резерв 45–60 минут | проверенный архив и rollback |

После двух попыток одного treatment без срабатывания механизма прекратить его повторять. Разобрать trace, выбрать предусмотренную ниже следующую развилку. Не тратить остаток времени на полные extra suites. Если выполнение занимает более одной сессии, записать текущий архив, последний результат и следующий шаг в HANDOFF; новая сессия продолжает, не запускает всё сначала. Финальную четверть доступного времени сохранить для повторов и P6.

## Команды существующего стенда
