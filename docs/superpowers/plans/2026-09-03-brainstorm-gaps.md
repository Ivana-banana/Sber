# Брейншторм: что упущено / что стоит добавить-исправить

Черновик для обсуждения, 03.09.2026. Не спецификация, код не менялся. Источники:
`PLAN.md`, `HANDOFF.md`, `docs/tz-compliance-audit.md`, `docs/experiments.md`
(E015/E016/E017), `agent/*.py`, `docs/decisions.md`.

## 0. Главный факт: узкое место — timeout, не reasoning

E017 (свежий accepted-candidate baseline на живой qwen2.5-coder:7b): **4/18**,
из 14 нулей **13 — timeout**, 1 — verification. Это значит: агент не "не умеет
решать задачи", а **не успевает**. Любое улучшение промпта/routing/verify не
даст эффекта, пока не решена причина таймаутов. Это должно быть приоритетом
№1 брейншторма, а не косметика промпта.

Гипотезы, что можно проверить (не решено, нужны абляции по одному фактору):

- сколько шагов/вызовов LLM уходит впустую на fixture с исходом timeout —
  возможно, модель зацикливается или делает избыточные inspect-шаги перед
  первым действием;
- `MAX_STEPS=30` (agent/limits.py:62) и `VERIFY_RESERVE_FRACTION=0.20` —
  стартовые числа, не откалиброванные на 7B; возможно, резерв верификатора
  слишком велик/мал именно для длинных forensic/audit задач;
- per-tool timeout vs общий wall-clock deadline — не видно поэтапной
  телеметрии "сколько времени ушло на что" в E017-summary, только итоговый
  таймаут. Нужен breakdown по фазам (inspect/plan/act/verify), иначе каждая
  гипотеза остаётся гаданием.
- endpoint_late=14 в E017 — это late replies, которые считаются в токены, но
  не факт что и в решаемость. Похоже на систематическую проблему generation
  speed самой 7B модели на длинных промптах, а не логики агента.

## 1. Observability пробелов

- Нет per-step тайминга в трассе (только итог: steps used, tokens, wall_s).
  Без этого нельзя отличить "модель тормозит" от "агент делает лишние шаги"
  от "verify съедает бюджет". Один из самых дешёвых по стоимости и самых
  ценных по сигналу апгрейдов.
- `docs/experiments.md` фиксирует zero taxonomy (timeout/verification/...),
  но не детализирует *где именно* внутри timeout-задачи произошла остановка
  (на каком шаге, какая была последняя гипотеза модели).

## 2. Незакрытые дыры безопасности контура (из самого аудита)

- `run_shell` (agent/tools.py:~210) принимает произвольную строку без
  ограничения путей/команд — единственный реалистичный self-enforcement
  (Landlock) не может быть подтверждён без ядра оценочной среды (BLOCKED,
  `docs/decisions.md:71`). Это осознанный TBD, но стоит явно решить: либо
  smoke-allowlist команд с измерением регрессии на CTF/forensic наборе, либо
  сознательно принять риск и задокументировать его как "не наш периметр".
- E015: 3/15 case дали реальные side effects от prompt injection (README,
  ANSI escape, cross-file). Ноль input mutations — хорошо, но 3/15 markers —
  не ноль. Нет ещё контролируемого security-vs-utility эксперимента (в очереди
  после текущей задачи по HANDOFF).
- Runtime docstrings всё ещё содержат имена public task/path/answer
  (`bye-file`, `fix-sqli-login`, `bye.txt`/`Bye`) — прямое нарушение
  CLAUDE.md "хардкод под public cases запрещён", даже если оно не влияет на
  runtime-ветвление. Дешёвая, но пока не сделанная правка.

## 3. Незакрытый organizational риск

- КТ №4 был отправлен вне Git 31.08 — нет тега, нет коммита с метриками
  отправленного архива. Rollback-кандидат для КТ №5 неизвестен. Это чисто
  процессный риск: если что-то пойдёт не так на следующей итерации, откатиться
  не на что. Стоит форсировать получение SHA/sha256/model/metrics от того,
  кто отправлял, до следующего freeze.
- G6 (exact ACP offline gate) не воспроизводится на текущем Docker daemon —
  только `python:3.12-slim` суррогат. Перед реальной отправкой КТ нужен
  подтверждающий прогон на pinned image, иначе "offline-совместимость"
  доказана лишь частично.

## 4. Возможные функциональные пробелы (не решённые, не факт что нужны)

- Нет ретрая/self-correction сверх одного recovery pass — по архитектуре это
  осознанное решение ("максимум один направленный проход"), но при 13/14
  нулей = timeout вопрос "а не тратит ли recovery pass бюджет впустую, если
  он всё равно не успевает" стоит явно измерить, а не просто принять на веру.
- Мультиагентность/router по типу задачи сознательно не строится (playbooks
  внутри одного prompt) — согласуется с CLAUDE.md ("Overfit a single batch
  first"), пересматривать преждевременно без данных о том, что именно
  единый контур не тянет.
- Нет token hard-cap — только учёт (PARTIAL в аудите). Значения hidden limit
  неизвестны, но при таймаут-доминирующей картине это вторично.

## 5. Что НЕ стоит трогать сейчас (явно зафиксировано документами)

- Language translation prompt (RU→EN) — измеримый эффект +155 токенов,
  но стоит в очереди позже security gate; не приоритет, пока не решена
  причина таймаутов.
- `.venv` pruning в preflight — однострочная правка, но без baseline
  абляции не измеряется; ждёт своей очереди.
- Ключевой вывод: пока 13/14 нулей — timeout, любые эксперименты с prompt
  compression / verification policy дают ложный сигнал, если не изолировать
  фактор "успевает выполниться" отдельно.

## 6. Синтез внешнего ресёрча (`deep-research-report.md`, добавлен пользователем)

Отчёт подтверждает диагноз из раздела 0 (timeout — узкое место) и даёт внешние
данные по способам ускорения ReAct-цикла на маленьких локальных LLM. Ниже —
что из него применимо к нашей архитектуре, а что нет, проверено по коду
(`agent/loop.py`, `agent/state.py`, `agent/main.py`, `agent/prompt.py`) и по
реальным логам E017 (`build/eval-E017-accepted-control/`), а не принято на
веру.

### 6.1 Главная находка сессии: телеметрия уже написана, но не долетает до логов

`agent/state.py:288-296` уже пишет `start_phase`/`finish_phase` (`plan`, `act`,
`verify`) с длительностью, `agent/main.py:30-37` уже подписан на них через
`state.event_sink = emit_phase` и печатает `agent phase: step=... phase=...
duration_s=...` в stdout. То есть **ровно тот per-step тайминг, который и
предыдущий аудит, и внешний отчёт называют приоритетом №1, в коде уже есть.**

Но: во всех 18 логах E017 (`build/eval-E017-accepted-control/logs/*.log`) —
`grep -c "agent phase"` даёт **0** совпадений, включая задачи, где было 4-7
реальных шагов и которые точно прошли через `start_phase`/`finish_phase`.
Логи содержат только строки `agent ready:` / `agent done:`. Значит поток
телеметрии либо не долетает до `scripts/eval/run_suite.py` (который честно
пишет `proc.stdout + proc.stderr` без усечения, `scripts/eval/run_suite.py:344-346`),
либо `event_sink` глушится по пути (в `state.py:277-280` любое исключение
внутри `event_sink` навсегда отключает его — `self.event_sink = None` — и это
специально задумано как fail-safe, но не залогировано, значит тихий сбой
неотличим от отсутствия сигнала).

**Это самая дешёвая и самая ценная задача из всего брейншторма**: разобраться,
почему `agent phase` не долетает до `.log`, прежде чем прогонять что-либо ещё.
Без этого любая гипотеза про LLM-latency vs число шагов vs verify остаётся
гаданием — ровно то, от чего предостерегает и наш собственный аудит, и отчёт.

### 6.2 Что уже сделано (репорт рекомендует то, что у нас есть)

- **Один вызов LLM на шаг, а не отдельно plan+act.** `agent/loop.py:92-99`
  делает один `llm.complete_structured` на итерацию, который сразу возвращает
  действие. Рекомендация отчёта №1 ("collapse planning and action into one
  generation") уже выполнена архитектурно — это не пробел.
- **`temperature=0`.** Подтверждено в E017-summary.txt. Рекомендация отчёта
  про детерминированный sampling уже в силе.
- **Rolling raw observation window, не rewrite-каждый-раз.** `agent/prompt.py:138-155`
  берёт последние `OBSERVATION_WINDOW` наблюдений и добавляет их как отдельные
  сообщения, не переписывает историю целиком. Это ближе к "immutable history"
  паттерну из раздела 6.4, чем к анти-паттерну "sliding-window rewrite",
  который отчёт явно предостерегает как убивающий prefix cache (раздел про
  CoACT). Стабильность префикса не проверялась отдельным экспериментом.

### 6.3 Что реально не наше — бэкенд не vLLM/llama.cpp

E017 использует **Ollama 0.20.5** (`model=qwen2.5-coder:7b-instruct-q4_K_M`),
не vLLM и не голый llama.cpp-сервер. Значит рекомендации отчёта про
`enable_prefix_caching=True` (vLLM API), AWQ-квантование через vLLM,
конкретные флаги speculative decoding в llama.cpp CLI — **не наш рычаг**:
мы не выбираем и не конфигурируем инференс-бэкенд, только шлём запросы через
`OPENAI_BASE_URL`/`LOCAL_AGENT_MODEL` (CLAUDE.md: "LLM доступна только
через..."). Целевая оценочная среда может использовать другой бэкенд/модель
вообще — фиксировать конкретную backend-оптимизацию как решение нельзя.

Что из этого блока остаётся полезным даже без контроля над бэкендом:
Ollama тоже кэширует контекст между запросами с общим префиксом (аналог APC),
так что "не портить префикс" — совет, применимый к нам независимо от бэкенда,
и это единственный пункт из блока backend-тюнинга, который стоит унести в
раздел 6.4.

### 6.4 Что применимо и не сделано — кандидаты на измерение (не решения)

- **Батчинг независимых read-only действий в одном шаге.** Сейчас
  `_execute` (`agent/loop.py:347`) выполняет один tool на итерацию. LLMCompiler-стиль
  ("несколько read-only команд одним решением") мог бы сократить число
  LLM-вызовов на inspect-тяжёлых задачах (forensic/audit), но это меняет
  контракт `ACTION_SCHEMA` и требует отдельной абляции — не тривиальная правка.
- **Детерминированное сжатие наблюдений по типу инструмента**, а не только
  окно последних N. Сейчас `agent/tools.py` уже режет/редактирует вывод (судя
  по докстрингу prompt.py про "already bounded and already redacted"), но
  неясно, насколько агрессивно — стоит проверить, не является ли сырой вывод
  `strings`/`readelf`/директорийных листингов доминирующей частью промпта на
  forensic-задачах, как показывает CoACT/TACO по чужим датасетам.
- **Живой оценщик "сколько раундов ещё влезет" вместо фиксированных
  `MAX_STEPS=30`** (`agent/limits.py:62`). У нас уже есть `Budget` с
  `may_act()`/`past_early_deadline()` (шаговый + дедлайн-контроль), но нет
  оценки p90 длительности раунда для решения "стоит ли начинать ещё один
  explore-шаг или сразу сворачиваться". Формула из отчёта (`R = deadline-now`,
  `N_fit = floor(S / round_latency)`) ложится на существующий `Budget` без
  архитектурной перестройки — но опять же, без данных из 6.1 это будет
  калибровка вслепую.
- **Checkpoint/best-known-state вместо attempt-to-finish.** Частично уже
  есть: `EARLY_DELIVERABLE_DEADLINE_S` заставляет писать промежуточный
  результат на диск (`agent/loop.py:83-88`). Чего нет — явного "если текущее
  состояние хуже уже сохранённого, откатиться к сохранённому" перед finish;
  сейчас, судя по докстрингу `Outcome`, `finish` либо проходит верификатор,
  либо не проходит, без сравнения с предыдущим лучшим артефактом.

### 6.5 Что стоит отклонить или отложить осознанно

- Speculative decoding (0.5B draft) и квантование — не наш периметр (см. 6.3),
  и даже если бы был наш: отчёт сам показывает пары модель/draft без ускорения
  (Gemma-2 9B/2B) — это должно тестироваться на конкретной паре, которую мы не
  выбираем.
- LLM-judge для early stopping отчёт сам называет контрпродуктивным
  ("an LLM judge is the wrong way to save LLM latency", раздел про semantic
  early stopping) — совпадает с нашим верификатором, который уже
  детерминированный (`agent/verify.py`), поэтому это не пробел, а
  подтверждение текущего решения.

## Рекомендация по порядку (не решение, предложение к обсуждению)

1. **Обновлено после 6.1**: сначала выяснить, почему уже существующая
   `agent phase`-телеметрия (`agent/state.py:288-296`, `agent/main.py:30-37`)
   не долетает ни до одного из 18 логов E017. Это не "добавить тайминг" —
   он уже есть в коде, — а найти и починить утечку/тихий сбой в конвейере
   логирования (`event_sink` disable-on-exception в `state.py:277-280`,
   либо потеря в `scripts/eval/run_suite.py`). Дёшево, потому что не требует
   нового прогона на модели — можно диагностировать локально с фиктивным LLM.
2. Прогнать (или переанализировать, если чинится без ре-рана) один
   timeout-fixture с полной трассой фаз, понять, где уходит время (LLM
   latency vs число шагов vs verify).
3. Только после этого — абляция MAX_STEPS/VERIFY_RESERVE_FRACTION/step
   timeout, по одному фактору. Из внешнего отчёта дополнительно проверить:
   живой p90-оценщик "сколько раундов ещё влезет" вместо фиксированного
   `MAX_STEPS=30` (раздел 6.4) — но только после того, как есть данные из п.1-2.
4. Параллельно (не блокируя п.1-3): обезличить runtime docstrings — это
   0-риск и явный compliance-долг.
5. Security gate (E015 recheck + контролируемый treatment) — по очереди из
   HANDOFF, не раньше и не позже.
6. Backend-специфичные оптимизации из внешнего отчёта (квантование,
   speculative decoding, explicit prefix-cache flags) сознательно не
   планируются — целевой инференс-бэкенд не под нашим контролем (раздел 6.3).
