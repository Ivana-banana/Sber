# Рост решаемости по тестам организаторов — план экспериментов

> **For agentic workers:** выполнять последовательно через `executing-plans`.
> Это план диагностики и независимых абляций; не реализовывать все изменения одним пакетом.

**Goal:** увеличить число содержательных задач организаторов, решённых настоящим
checker, сохранив ранее решённые задачи и затем снижая токены.

**Architecture:** сохраняем один цикл и stdlib runtime. Улучшаем доступ модели к
доказательствам, локализацию работы и проверку результата отдельными факторами.
Форматные проверки дополняют поведенческий oracle, но не заменяют его.

**Tech Stack:** Python 3.12, существующие `agent/`, pytest разработки,
`scripts/eval/run_suite.py`, Docker/Harbor, текущая локальная 7B-модель.

**Spec:** [docs/task.md](../../task.md),
[аудит кода, официальных проверок и трасс](../../research/organizer-first-audit-2026-09-07.md).

## Ограничения и критерий успеха

- Закрытый набор — 15 независимых задач; каждая даёт 1 или 0.
- Runtime без интернета и без установки зависимостей; архив не более 10 МБ,
  executable `run.sh` в корне, контракт `./run.sh "<task instruction>"`.
- Не использовать имена задач, эталонные значения, evaluator `/tests` или
  reference solutions в агенте. Для разработки внешние official checkers — основной судья.
- Сначала solved, затем input+output tokens, затем wall time.
- Наборы считать отдельно: шесть public организаторов; 18 наших диагностических
  задач; новые мутации для контроля обобщения. Не складывать их в headline «x/24».
- Фиксировать поимённо gained/lost: равный solved при потере прежней победы
  не является приёмкой. Изменение формата/верификации, не меняющее reward,
  закрывает свой механизм, но не объявляется улучшением решаемости.
- Каждый фактор: исходный красный replay → минимальная правка и unit/contract →
  целевой public-кейс → полный public set → 18 regressions → повторы control/treatment.
- При стохастике минимум три повтора каждого плеча; temperature=0 не гарантирует
  детерминизма. Первые короткие пилоты отбрасывают провалившиеся идеи до дорогой серии.
- Архитектурную гипотезу записывать в `docs/decisions.md` до/вместе с кодом;
  результаты и hashes — в `docs/experiments.md`; отдельный коммит на фактор.

## 3. Проверять исправленное поведение и возвращать причину провала

**Файлы:** `agent/verify.py`, `agent/loop.py`, `agent/playbooks.py::CODE_FIX`,
`tests/test_verify.py`, `tests/test_loop.py`. Это последовательные абляции 3a–3c.

- [ ] **3a, обратная связь:** на красной команде передать bounded/redacted failed
  assertion или stderr с указанием сохранённого полного вывода; проверить, что
  секреты и длинный traceback не раздувают контекст. Не менять критерий ok этим фактором.
- [ ] **3b, процедура fix:** запускать указанную пользователем `pytest tests/` из
  workspace с установленным interpreter; сохранить исходный результат, воспроизвести
  security-дефект, исправить, повторить negative probe и нормальный regression suite.
  Успешный pytest обычной функциональности сам по себе не доказывает устранение SQLi.
- [ ] **3c, контракт:** различать existence/format и behavior/evidence. Пустая
  verify-команда означает unverified; print/наличие ключей — smoke/format, а не
  доказательство security/форензики. Не превращать запрет `print` в новый универсальный
  парсер shell: реальные проверки могут сочетать assertions и печать.
- [ ] Воспроизводящие сценарии: redirect с похожим hostname; SSH с ключами и
  неподтверждёнными значениями; check после shell-правки; несколько изменённых модулей.
  Тесты обязаны подтверждать поведение и независимость ожидаемого результата от
  только что записанного кандидата. Отказ не должен уничтожать последний артефакт.
- [ ] После пилота выполнить official login/search fix checkers и обычные tests;
  сделать чистый перезапуск приложения/БД внешним harness.

**Приёмка:** воспроизведённые ложные успехи перестают завершаться как доказанное
решение; оба вида тестов реально исполняются. Новая reward-победа учитывается отдельно.
Нельзя считать «два false positive стали stuck» ростом solved.

## 4. Форензика: вычислить значения, сохранить происхождение

**Файлы:** `agent/playbooks.py::FORENSICS`; дальнейшая работа с памятью отдельно
в `agent/state.py`, `agent/prompt.py`; eval-fixtures — `local_task_extra/`.

- [ ] Один фактор: короткая процедура «manifest всех источников → маленький Python
  parser по реальным полям → join → таблица кандидатов со ссылками на строки → вывод».
  Использовать stdlib `json`, `re`, `datetime`, а не передавать большие логи целиком LLM.
- [ ] Не останавливаться на primary log, когда note сообщает о recovered/shards;
  различать отсутствие файла, отсутствие совпадения и ошибку парсера.
- [ ] Для каждого итогового поля сохранять source path + исходную строку/ключ события.
  Исходный timestamp копировать, даже если для сортировки вычислено другое представление.
  Правила выбора события и XFF выводить из материалов конкретной задачи;
  «первый IP», «максимальные bytes», «последний public hop» не универсальны.
- [ ] Official pilot — `incident-log-forensics`: все четыре значения сверяются
  официальным `test.sh`. `check_parity.py` использовать только разработчику для
  диагностики данных, не выдавать агенту как решатель.
- [ ] Мутации: переставить записи, переименовать файлы, перенести решающее событие
  в shard, поменять logical/transport bytes и fractional timestamp; expected
  вычислять независимо. Ровно один механизм мутации на сравнение.

**Приёмка:** official reward 1 с полным набором источников и без добавления новых
runtime-зависимостей; unknown не заменяется угаданными значениями ради формы.

## 6. Направленный recovery и завершение

**Файлы:** `agent/loop.py::run/_finalise/_deliverable`, `agent/state.py`,
`tests/test_loop.py`, `tests/test_budget.py`.

- [ ] После первых факторов пересчитать: модель не вызывает finish, finish
  отклонён по контракту, проверка красная или формально зелёная. Лечить доминирующий путь.
- [ ] На stuck с кандидатом выполнить доступный релевантный check в пределах резерва.
  Зелёный → оставить кандидат и завершить. Красный → один recovery с конкретной
  ошибкой и другой веткой действий. Нет oracle → unverified, без выдуманного успеха.
- [ ] Не снимать stop вообще: E028/E029 показали потерю уже правильных результатов
  от дальнейшей перезаписи. Перед recovery сохранить версию; возвращаться к ней
  только при наличии ранее подтверждённой проверки, а не по размеру файла/числу слов.
- [ ] Проверить исправление через shell и несколько файлов как результат code-fix,
  а не требовать искусственный report ради существования единственного path.
- [ ] Budget-тесты: recovery не начинается внутри резерва; один pass; проверка
  не повторяется бесконечно; при ошибке и внешнем timeout кандидат сохранён.

**Приёмка:** раньше достигнутый верный ответ не портится, хотя бы один прежний
public-ноль исправляется направленным recovery. Рост `claim=True` без reward не успех.

## Контроль обобщения и выпуск

Мутации нужны с первого принятого улучшения, а не после «6/6». Первые — изменения
official-формы: межфайловая SQLi, другие имена параметров, безопасный lookalike,
recovered/sharded forensic, изменённые значения и формат требований. Часть новых
вариантов заморозить до подбора prompt и держать отдельным holdout. Расширять
непривязанный к данным набор из 18 задач раньше этого шага не приоритетно.

Финальная приёмка кандидата: сохранены все прежние official-победы, воспроизводимо
добавлена содержательная; диагностические и holdout результаты опубликованы отдельно;
нет известных startup/packaging регрессий. Затем собрать фактический zip, проверить
offline в целевой среде и повторить public smoke после распаковки именно этого zip.
Работа с документацией сегодня не означает разрешения считать эти будущие шлюзы пройденными.
