## Сборка архивов — ровно эти команды

Ровно эта последовательность вечером дала оба опубликованных SHA. Собирай из
**чистого экспорта коммита**, а не из рабочего дерева: в рабочем дереве лежат чужие
незакоммиченные правки, и архив из него — уже не тот коммит.

```sh
out=$PWD/build/kt7            # каталог для архивов, любой вне экспорта
mkdir -p "$out"
for sha in fc82507 0c96797; do
  tmp=$(mktemp -d)
  git archive "$sha" | tar -x -C "$tmp"
  ( cd "$tmp" && python3 scripts/build_submission.py --out "$out/$sha.zip" )
  rm -rf "$tmp"
done
sha256sum "$out"/fc82507.zip "$out"/0c96797.zip
```

Сверь SHA-256 с двумя значениями выше **до** первого прогона. Если не совпало —
остановись и разберись: значит, ты собираешь не то, что поедет организаторам.

## Гигиена стенда — читать обязательно, здесь уже теряли ночи

- **Убедись, что модель реально на GPU.** На машине владельца `--gpus all` падал и
  ollama молча уезжал на CPU, после чего все задачи умирали по таймауту, а прогон
  выглядел как «агент стал хуже». После старта проверь `ollama ps`: должно быть
  100% GPU, не `NN%/NN% CPU/GPU`. Запиши это в карточку.
- **Зафиксируй `n_ctx` и не меняй его в Блоке 0.** Вся история проекта снята при
  `CONTEXT=4096`. Чтобы твои числа можно было сравнить с `9/18` отката, окно должно
  быть тем же. Окно варьируется только в H3 и только отдельным прогоном.
- Параметры, одинаковые для всех прогонов Блока 0 и 1: `--timeout-scale 1.0`,
  **без** `--tell-agent-budget`, `temperature 0`, модель
  `qwen2.5-coder:7b-instruct-q4_K_M`, контроллер по умолчанию (`loop`, не `macro`).
- Во время зачётного прогона на этой машине не запускай pytest, сборку образов и
  вторую модель. В аудите 17.09 прямо записано, что R2A и часть R2B-public шли
  одновременно с полным pytest, и это испортило сравнение.
- Каталоги `--out` уникальны, старые не перезаписывать.

## Блок 0 — какой архив везём. Блокирует сдачу

Два прогона, `public` (6 задач организаторов), по **5 повторов** каждый.
На 4080 с полностью выгруженной 7B это недорого; 5 повторов нужны не для красоты, а
потому что весь проект утонул в дрейфе ±3 задачи на n=1..3.

```sh
python3 scripts/eval/run_suite.py --tasks-root local_task \
  --archive <путь>/fc82507.zip --repeats 5 --timeout-scale 1.0 \
  --model qwen2.5-coder:7b-instruct-q4_K_M --base-url <endpoint> --api-key ollama \
  --label KT7-cand-public --out build/eval-KT7-cand-public

python3 scripts/eval/run_suite.py --tasks-root local_task \
  --archive <путь>/0c96797.zip --repeats 5 --timeout-scale 1.0 \
  --model qwen2.5-coder:7b-instruct-q4_K_M --base-url <endpoint> --api-key ollama \
  --label KT7-roll-public --out build/eval-KT7-roll-public
```

Запусти их **подряд на одной машине в одну ночь**. Опубликованные `9/18` у отката
сняты в других условиях и сами по себе основанием не являются.

### Правило решения — записать в карточку ДО запуска

Обозначь `C` = eligible кандидата из 30, `R` = eligible отката из 30.

- **`C >= R - 3`** → **везём кандидат `fc82507`.** Ничья и мелкое отставание
  трактуются в пользу кандидата сознательно: его правки (ответ списком текстовых
  частей, 429, отказ thinking-параметра, исключение инструмента вместо падения,
  переполнение контекста, CRLF, OverflowError в поиске, redaction) закрывают класс
  **жёстких нулей на неизвестном endpoint**, а 7B-стенд этот класс почти не создаёт —
  он его и не измерит. Дельта внутри дрейфа не перевешивает защиту от отказа, из
  которого нет возврата.
- **`C < R - 3`** → это уже не шум. Разобрать по задачам, какие именно потерялись,
  и если причина не воспроизводится как дефект стенда — **везти откат `0c96797`**.

Правило зафиксировано заранее именно потому, что в этом проекте числа регулярно
объяснялись задним числом. Не меняй его после того, как увидишь результат.

### Что снять помимо solved

Из `suite.json` и `manifest.json`: complete, число уникальных `(task, repeat)`,
`eligible_success`, `timed_out`, input/output/total tokens, wall. Отдельно —
**разброс по повторам на каждой задаче**: какие задачи дрожат, какие стабильны.
Эта таблица дороже самого solved: она говорит, какую дельту стенд вообще способен
различить, и делает читаемыми все будущие абляции. `summarise.py` считает стоимость,
но его сырой `reward == 1` не заменяет `eligible` — правильный файл после таймаута
зачётом не является.

## Блок 2 — гипотезы. Только после Блоков 0 и 1, по одному фактору за прогон

Общее правило: control — кандидат `fc82507` из Блока 1, те же 18 фикстур, те же 3
повтора, меняется ровно одна вещь. Предсказание записывается в
`docs/research/live-runs/<H>-prediction.md` **до** запуска, включая условие

### H1 — best-snapshot плюс право не останавливаться по `stuck`. Приоритет высший

Самая обоснованная связка из всех, что у нас есть, и единственная, где два известных
результата смыкаются.

В `agent/loop.py` на ветке `stuck` стоит комментарий, объясняющий, почему выход
оставлен: E028/E029 сняли его безусловно и **измерили обе половины размена** —
`fix-redirect-scheme` был выигран дважды, `mut-salutation-beacon` дважды проигран,
потому что прогон тратил оставшиеся шаги на переписывание файла, чей верификатор уже
был зелёным. Дословно: *«у прогона нет оракула, который сказал бы, какая версия была
хорошей, поэтому единственная версия, которую он может защитить, — та, что на диске
сейчас»*.

**P1 `best-snapshot` — это ровно тот недостающий оракул.** Ветка `agent/best-snapshot`,
коммит `b840daf`, код и тесты готовы (283 зелёных), живого гейта не было. В JOURNAL
записана верная поправка, что **P1 в одиночку не даёт ничего** — и это согласуется:
P1 создаёт свободу, которой никто не пользуется, пока `stuck` по-прежнему обрывает
прогон. Пара должна дать то, чего не даёт ни одна половина.

- Меняем: P1 поверх кандидата **плюс** снятие/ослабление обрыва по `stuck` при
  условии, что deliverable существует и осталось больше половины бюджета.
- Не меняем: prompt, playbook'и, бюджеты, `verify.py`, набор инструментов.
- Предсказание записать заранее. **Условие опровержения:** возвращаются потери класса
  `mut-salutation-beacon` (задача была решена в control и обнулилась). Если они
  вернулись — ранжирование «здоровья» в P1 неверно, и пару не принимаем.
- Абляцию половинками (только P1, только снятие `stuck`) делать **лишь** если пара
  дала эффект; иначе это трата ночи на подтверждение известного нуля.

### H2 — finish без проверки, которая способна провалиться

В `agent/verify.py` стадия `STAGE_UNVERIFIED` возвращает **`ok=True`**: если модель не
дала verify-команду, прогон завершается на одних только «существует, непустой, не
исходный». Содержание не проверяется никогда. Это прямо объясняет разрыв
«deliverable 17/18 против solved 5/18».

- Меняем: когда verify-команды нет, а резерв бюджета ещё есть — **один** дополнительный
  вызов с требованием команды, которая упала бы на неверном ответе. Механизм `_cannot_fail`
  (E032) для отбраковки `cat`, `|| echo` и конвейеров читателей уже написан, его
  переиспользовать, а не писать заново.
- **Критично:** это совет, а не отказ. Запрет завершаться без самопроверки выдумывает
  правило, которого у настоящего верификатора нет (M13, `docs/research/verdict-verifier-contract.md`);
  реальный чекер читает среду независимо от того, что мы тут запустили. Ошибка в эту
  сторону обнуляет верные ответы.
- Условие опровержения: растёт число `verification`-нулей либо падает solved.

### H3 — окно контекста в новом режиме. Диагностика, не изменение агента

E026 уже проверял 4096 → 16384 и получил 2/18 против 3/18, вывод «окно не ограничивает».
Но снято это было на старом архиве, **в одном повторе**, и главное — в режиме, где
две трети всех отказов были таймауты. E048 показал, что на GPU класс таймаутов исчезает
полностью, а число вызовов на задачу растёт с 7–11 до 24–28. Истории стало втрое
больше, а окно осталось 4096 при промпте агента около 3000 токенов — на всё остальное
примерно тысяча.

Прогони кандидат при `CONTEXT=16384`, 18 фикстур, 3 повтора, против control из Блока 1.

**Этот результат нельзя «внедрить»** — окно задаёт endpoint организаторов, не мы.
Его ценность в другом: если solved заметно вырастет, значит вся наша история измерена
в искусственно узком режиме, и часть принятых факторов — артефакты стенда. Это меняет
доверие к сравнению из Блока 0, а не код.

### H4 — переносимость между размерами модели. Тоже диагностика

На 4080 помещается 14B Q4 целиком. По карточкам команды одна и та же кодовая база даёт
6/18 на 7B и 17/18 на 30B — модель решает больше, чем любой наш фактор, а модель
оценки нам неизвестна.

Прогони **оба** архива на 14B, `public`, 3 повтора.

Смысл строго решающий: если порядок кандидата и отката на 14B **тот же**, что на 7B —
сравнению из Блока 0 можно верить. Если порядок **перевернулся** — 7B-сравнение не
является основанием для выбора, и тогда везём кандидат по соображению устойчивости
(его правки закрывают жёсткие нули), а не по solved.

## Чего не делать

- **Не вливай P3 (JSON-guard на `write_file`, `f6c10cb`) вслепую.** Он трогает
  инструмент, которым пользуется каждая задача. Без парного замера это ставка против
  измеренного архива.
- **Не трогай prompt.** E034 (порядок блоков) — 2/18, не подтверждён. E042/E046
  (английский резидент) — 3/18 и 2/18 против 3/18 и 3/18, первый критерий проигран,
  причём `mut-audit-query-gate` даёт 2/2 под русским и 0/2 под английским.
- **Не возвращай `r2/general`.** Отменена критиком: веса роутера роняли форензику
  19/20 → 9/20, срез заголовка выдумывал exact-file контракт, исключение `/etc` не
  работало на реальном пути и ослабляло проверку симлинков.
- **Не переключай `DEFAULT_CONTROLLER` на `macro`.** Предзарегистрированное условие
  пилота (≥4/5) не взято: E044 дал 1/5, E045 на полной сюите — 0/13 к моменту остановки.
- Не меняй два фактора за прогон и не повышай лимиты эпизодов ради расписания.
- Не сокращай публичный набор.
