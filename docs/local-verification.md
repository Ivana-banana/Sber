# Что и где можно проверить локально

Файл отвечает на один вопрос: какой прогон какое утверждение доказывает. Он нужен
потому, что «тесты зелёные» и «архив стартует у организаторов» — разные утверждения,
а расстояние между ними измеряется ступенями ниже. Ступень никогда не доказывает
утверждение следующей.

## Ступени

| # | Среда | Запуск | Что доказывает | Чего не доказывает |
|---|---|---|---|---|
| 1 | Windows | `python -m pytest -q` | чистую логику и метаданные собранного архива | ничего про POSIX-права: Windows не умеет `exec` для `.sh`, поэтому contract-прогон preflight здесь честно даёт SKIP |
| 2 | WSL2 `ozon`, Ubuntu 22.04.5 | `wsl -d ozon` | распаковку настоящим `unzip`, exec-бит, `./run.sh` без единой починки, полный pytest на Linux | что это целевая среда: Python 3.10 против 3.12 и другой набор утилит |
| 3 | Docker внутри WSL2 | `docker` 29.6.1 (Server, overlayfs) | старт в произвольном образе, в том числе `--network none` | что это **тот** образ, пока он не скачан по digest |
| 3.5 | ФС `secureintelligent/acp`, `chroot` + `unshare --net` | выполнено внешним прогоном M12 | G1 (компоновка), контракт аргументов и exit code, dash-совместимость `run.sh`, состав утилит и Python — исполнением, а не по списку пакетов | что это контейнер: нет Harbor wrapper, cgroups, seccomp и смонтированных `/proc`, `/sys` |
| 4 | `secureintelligent/acp` offline, `docker run --network none` | выполнен 2026-08-25, образ скачан по digest, см. `E003` | G6: contract-запуск `./run.sh` без `chmod`, побайтовый round-trip текста, коды выхода, обе компоновки, отсутствие сети | лимиты оценочной microVM (`nproc`/память принадлежат хосту WSL2), Harbor wrapper и решаемость |

## Проверено 2026-08-25

Ступень 2 — на собранном архиве, каталог распаковки внутри `/tmp`:

```
unzip текущего архива          -> -rwxr-xr-x, ./run.sh exit 0, ничего не чинилось
unzip пересборки с DOS-host    -> -rw-r--r--, ./run.sh: Permission denied
python3 -m pytest tests/test_submission.py  -> 28 passed
python3 scripts/check_submission.py         -> PASS cold start contract
```

Ступень 3 — только факт работоспособности движка:

```

curl registry-1.docker.io/v2/  -> 401 (ожидаемый ответ без токена, сеть есть)
docker images    -> целевого образа нет, лежат четыре чужих
```

Ступень 3.5 — прогон собранного архива в восстановленной ФС образа
(`docs/research/submission-execution-check.md`, разбор — `verdict-submission-execution-check.md`):

```
15 непустых инструкций  -> exit 0, 367-416 мс, статусная строка, ни traceback, ни зависаний
пустая строка / нет arg -> exit 2, usage: run.sh "<task instruction>"
layout archive-root     -> run.sh прямой файл каталога агента, контракт принимает
layout one-top-level    -> run.sh под payload/, контракт НЕ принимает
```

Проверка достоверности с нашей стороны: пять инструкций пересчитаны через
`agent.main.fingerprint` — совпали все пять, значит текст задачи дошёл побайтово и
исполнялся именно наш код.

Граница ступени 3.5 названа явно: `/proc` и `/sys` в отчёте пусты, `nproc=6` и объём
памяти принадлежат хосту исполнителя. Это свойства chroot-песочницы, а не образа, и
переносить их в контракт нельзя.

## Ловушка: `/mnt/d` не хранит права

DrvFs показывает `-rwxrwxrwx` для любого файла независимо от `chmod`:

```
/mnt/d после chmod 0644 -> -rwxrwxrwx
/mnt/d после chmod 0755 -> -rwxrwxrwx
/tmp   после chmod 0644 -> -rw-r--r--
```

Значит распаковка в рабочий каталог проекта делает проверку exec-бита бессмысленной:
пройдёт любой архив, включая заведомо сломанный. `scripts/check_submission.py`
распаковывает через `tempfile.TemporaryDirectory()`, то есть в `/tmp`, и потому
измеряет настоящие права. Ручные проверки обязаны делать то же самое.

Вторая ловушка — не в Linux, а на пути к нему: Git Bash на Windows калечит аргументы
для `wsl.exe`, и присвоенные в скрипте переменные приходят пустыми. Скрипт надёжнее
передавать через stdin (`wsl -d ozon -- bash -s <<'EOF'`), иначе проверка молча
исполняет не то, что написано.

## Что это меняет

Запись в `HANDOFF.md` от 2026-08-24 («на машине нет Docker») описывала Docker Desktop
на Windows и запуск самого дистрибутива. Движок внутри WSL2 работает, поэтому G1 и G6
больше не ждут чужой машины: остаётся скачать образ по digest
`sha256:1324d7bb…c8a3` (~634 МБ) и прогнать старт собранного архива с `--network none`.

После ступени 3.5 G1 закрыт, а G6 сузился до одного вопроса: даёт ли контейнер с его
cgroups, seccomp и смонтированным `/proc` тот же результат, что и chroot по той же
файловой системе. Ответ стоит одного прогона и не должен откладываться до релиза.

Ограничение ступени 2 формулируется явно: Ubuntu 22.04 с Python 3.10 — это Linux, но
не `secureintelligent/acp`. Всё, что зависит от версии интерпретатора или состава
утилит образа, ступень 2 не проверяет и проверять не может.
