# Разбор M10: грабли упаковки zip и preflight

Дата: 26.08.2026. Источник — `packaging-pitfalls.md` (запрос M10 из
`docs/prompts/manus-prompts.md`), sha256
`213fdd4c5faefe5af4841272780773da9b782694cffc6f2ab62a5115822225a5`.

Отчёт пришёл с готовым `preflight_submission.py`. У нас такой скрипт уже есть —
`scripts/check_submission.py` от 25.08. Поэтому разбор свёлся к одному вопросу: что
из перечисленного наш чекер действительно ловит. Проверено не чтением, а сборкой
архива на каждый класс дефекта.

## 1. Достоверность

Механика ZIP описана верно и совпадает с тем, что уже реализовано у нас: Unix-режим
живёт в старших 16 битах `external_attr` и читается только когда `create_system = 3`.
Это ровно то, что делают `scripts/build_submission.py:100` и
`scripts/check_submission.py:194–216`. Ссылки [1]–[5] (APPNOTE, `zipfile`,
`execve(2)`, `Compress-Archive`, 7-Zip) — первичные, не проверялись повторно.

Существенно, что отчёт сам ограничивает свой вывод: `PASS` означает «архив
соответствует проверяемому статическому контракту», а не «решение получит ненулевой
балл». Это совпадает с оговоркой в docstring нашего чекера и с тем, что шлюз B
закрывается только прогоном в целевом образе.

Отчёт не знал про `sample_submission.zip` с вложенным верхним каталогом, но
независимо пришёл к тому же выводу: layout надо подтверждать реальным extractor'ом
runner'а, а не догадкой. Наш чекер уже трактует вложенный `run.sh` как FAIL с прямой
отсылкой к нерешённому вопросу.

## 2. Измерение: что наш чекер ловит на самом деле

Собран отдельный архив на каждый класс дефекта из таблицы отчёта, каждый прогнан
через `scripts/check_submission.py` отдельным процессом. Baseline — корректный архив
с `run.sh`, который печатает ожидаемый отпечаток инструкции.

| Класс дефекта | Результат |
|---|---|
| корректный архив (контроль) | PASS — верно |
| `agent\main.py` — обратный слеш в имени | **пропущен** |
| `C:/evil.txt` — имя с буквой диска | **падение чекера**, `FileNotFoundError` |
| член-симлинк (`S_IFLNK` на `/etc/passwd`) | **пропущен** |
| UTF-8 BOM перед `#!` | пойман (сообщение «has no shebang») |
| одиночный `CR` вместо `CRLF` | пойман косвенно — cold start падает |
| член 11 МиБ, сжатый до единиц КБ | **пропущен** |
| не-ASCII имя без флага UTF-8 (EFS) | **пропущен** |

Причина пропуска обратного слеша и буквы диска — платформенная:
`check_submission.py:149` использует `Path(name).parts`, а на Windows `WindowsPath`
разбирает `agent\main.py` в `('agent', 'main.py')` и не видит ничего опасного. На
Linux это было бы одно имя файла. Мы собираем архив на Windows, и это именно тот
случай, который правило «проверяй артефакт, а не дерево исходников» должно закрывать.

**Падение на `C:/evil.txt` — дефект хуже пропуска.** `apply_declared_modes`
(`check_submission.py:214`) делает `(dest / info.filename).chmod(mode)`. `extractall`
имена санирует, а этот `chmod` — нет: `dest / "C:/evil.txt"` на Windows схлопывается
в абсолютный путь, и наш собственный preflight пытается менять права файла **вне
каталога распаковки**. Здесь он упал, потому что файла нет; при существующем файле он
бы отработал. Недоверенный архив управляет операцией над ФС в нашем инструменте.

## 3. Честная оценка риска

Ни один из пяти пропусков не достижим нашим текущим билдером:
`scripts/build_submission.py` работает по allowlist, формирует имена через
`.as_posix()` и жёстко ставит `stat.S_IFREG`. Обратный слеш, симлинк, буква диска и
11-мегабайтный член из него получиться не могут.

Значит формулировка не «наш submission сломан», а «чекер не выполняет собственную
доктрину». Его docstring обещает проверять файл на диске, потому что артефакт «может
быть собран старой версией билдера, скопирован между машинами, обрезан при передаче
или отредактирован руками». Против ровно этих сценариев перечисленные проверки и
нужны. Приоритет — средний, кроме `chmod`, который правится как дефект.

## 4. Что принято

Пять проверок добавляются в `scripts/check_submission.py` (отдельной задачей, тестом
вперёд — измеренная таблица §2 и есть спецификация этих тестов):

1. Санировать имя до любой операции ФС: запретить `\`, ведущий `/`, `..` и
   `^[A-Za-z]:`. Разбирать через `PurePosixPath`, а не `Path`, — имена в ZIP
   POSIX-овые независимо от платформы сборки. Это же чинит падение из §2.
2. Отвергать члены-симлинки и любые типы, кроме `S_IFREG` и каталога.
3. Проверять `info.file_size`, а не только размер архива.
4. Требовать флаг `0x800` для не-ASCII имён.
5. Ловить одиночный `CR`, а не только `CRLF`, и явно называть BOM вместо
   «has no shebang».

Проверка на ZIP64 из отчёта принята как идея, но ниже приоритетом: наш архив 49 КБ,
`allowZip64` при таком размере не срабатывает.

## 5. Что отклонено

| Предложение | Решение | Причина |
|---|---|---|
| **`NETWORK_PATTERNS`: FAIL/WARN на `socket`, `subprocess`, `urllib.request`, `https?://`** | **отклонено** | Прямо противоречит нашему контракту. Агент **обязан** ходить в `OPENAI_BASE_URL` через `urllib` и **обязан** запускать инструменты через `subprocess`. Эта проверка сработала бы на корректном submission. Отчёт писал её под допущение «сети нет вообще», а у нас офлайн — это отсутствие интернета при наличии локального endpoint |
| `INSTALL_PATTERNS` (`pip install`, `apt-get`) | **принято** | Здесь допущение верное: ставить зависимости во время прогона нельзя. Ложные срабатывания возможны в документации, но цена пропуска выше |
| Сканирование содержимого на секреты (`BEGIN PRIVATE KEY`, `api_key=`) | принято как WARN | У нас уже есть запрет по именам (`.env`, `.pem`, `.key`) и `agent/redact.py` на логах. Сканирование содержимого — дешёвый добавочный слой |
| Заменить наш чекер на `preflight_submission.py` | **отклонено** | Их скрипт статический. Наш дополнительно **исполняет** entrypoint с враждебным аргументом (кавычки, `$`, обратный слеш, перевод строки) при мёртвом endpoint и проверяет, что текст задачи дошёл неискажённым. Отчёт сам пишет, что статически это недоказуемо. Мы берём проверки, а не скрипт |
| `build_submission.py` из архива отчёта | отклонено | Наш билдер уже делает allowlist, сортировку, фиксированные timestamp и явные `external_attr`; отчёт это подтверждает как верный принцип |

## 7. Ограничение разбора

Таблица §2 получена на Windows. Часть результатов платформозависима: на Linux
`Path(name).parts` вела бы себя иначе для обратного слеша. Это усиливает вывод, а не
ослабляет — чекер обязан давать один вердикт на обеих платформах, а сейчас не даёт.
Ни одна из проверок не приближает шлюз B: он закрывается только прогоном в целевом
образе.
