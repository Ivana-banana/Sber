# Сопоставление клиентского кода и поведения локальных серверов

## Подтверждённые расхождения

| Код | Подтверждённая реальность | Последствие |
|---|---|---|
| `LlmSettings.missing()` считает пустой `OPENAI_API_KEY` фатальной конфигурационной ошибкой (llm.py:92–96); probe использует ту же проверку (probe_endpoint.py:58–62). | vLLM требует ключ только если включён `--api-key`/`VLLM_API_KEY`; SGLang по умолчанию имеет `--api-key=None`; llama.cpp требует его только при `--api-key`; LM Studio и локальный Ollama по умолчанию keyless; TGI-примеры используют заполнитель `-`. | Агент и probe не сделают ни одного запроса к обычному локальному endpoint без искусственного непустого значения переменной. Это расходится минимум с vLLM, SGLang, llama.cpp, Ollama и LM Studio. |
| Для native tools `_build_body()` всегда добавляет named OpenAI-object `tool_choice={"type":"function","function":{"name":"emit_action"}}` (llm.py:239–246). | Ollama в своей таблице OpenAI compatibility явно помечает `tool_choice` как неподдерживаемый. TGI в документированном forced-choice примере использует строку имени инструмента, не OpenAI object. | Ollama может отвергнуть native rung или проигнорировать field; TGI не обязан принимать эту форму. Лестница понизится не из-за качества модели, а из-за транспорта/диалекта сервера. |
| `_read_reply()` принимает только `tool_calls` как непустой **list**, а `function.arguments` как **str** (llm.py:284–291). | Документированный TGI пример возвращает `tool_calls` объектом и `function.parameters` как JSON-object. | Даже успешный инструментальный ответ TGI объявляется `unusable`, client понижает rung и теряет корректный результат. |
| При `style=JSON_SCHEMA` body использует современную OpenAI nested-форму `response_format.json_schema={name, schema, strict}` (llm.py:247–251). | Текущая llama.cpp-документация показывает другой контракт: `response_format={"type":"json_schema","schema":{...}}`, без вложенного `json_schema`. Старый TGI до merge #3046 требовал `type=json_object`/`json` с полем `value`, а не `type=json_schema`. | Для llama.cpp по документации JSON-schema rung может получить отказ и без необходимости перейти на `json_object`, а старый TGI минует schema enforcement на двух верхних JSON rung. |
| `_attempt_loop()` понижает протокол на **любом** HTTP 4xx, не анализируя ни статус, ни тело (llm.py:347–357). | Ollama документирует 400 как malformed/missing request, 404 как отсутствующую модель и 429 как rate limit. llama.cpp документирует 401 для неправильного ключа. | Ошибки модели, маршрута, ключа и перегрузки ошибочно воспринимаются как «текущий protocol shape не поддержан». В частности, 429 не ждётся, а делает до трёх неуместных downgrade и permanently понижает стиль. |
| На любом 5xx код ретраит **тот же** body/style (llm.py:341–345, 386–394). | llama.cpp #22072 фиксирует 500 `Failed to parse tool call arguments as JSON` из-за незаконченных аргументов. При temperature=0 та же детерминированная генерация/парсинг может повторить этот же отказ. | Расходятся с заявленным правилом «не повторять тот же уровень»: тратятся дополнительные запросы и время, а не выполняется переход native tools → JSON. |
| В native rung применяется только `calls[0]` (llm.py:284–291), а все остальные вызовы игнорируются. | vLLM указывает, что `tool_choice="required"` гарантирует один **или более** tool calls; LM Studio описывает, что модель может вызвать «one or more tools». Кроме того, vLLM #30372 подтверждает повторные tool-call loops. | При нескольких вызовах клиент молча сохраняет лишь первый. Для протокола с единственным `emit_action` это всё равно скрывает повторную/конфликтующую генерацию вместо маркировки её как дефектной. |
| После `json.loads` никакой проверки результата против переданной schema нет (llm.py:300–304). | vLLM #30372 показывает валидные JSON tool calls с искажёнными именами аргументов; LM Studio предупреждает, что small/not tool-trained models могут выводить неправильно сформированные calls. | Синтаксически валидный, но schema-некорректный объект признаётся успехом и передаётся дальше. В частности, отсутствующий required key, лишний key или мутированное имя не инициируют fallback/error. |
| Отсутствие `tool_calls` в native rung трактуется как полностью непригодный ответ (llm.py:284–288). | vLLM #17161 и документация LM Studio показывают случаи, в которых вызов остаётся в `message.content` (у LM Studio — при неудаче parser), а `tool_calls` пуст. | Корректно сериализованная попытка action в `content` не диагностируется и не извлекается; клиент понижает формат, меняя prompt вместо различения parser/server defect. |

## Что в коде согласовано с источниками

| Механизм | Оценка |
|---|---|
| Non-streaming запросы | Снижает число несовместимостей streaming: SGLang и Ollama указывают особые правила выдачи usage в stream; клиент stream не включает. |
| При отсутствии поля `usage` пометка `usage_reported=False` | Соответствует осторожной стратегии: LM Studio не документирует `usage` в кратком Chat Completions reference, а нативный Ollama использует другие имена счётчиков. Код не выдумывает метрику. |
| Salvage на TEXT rung | Покрывает префикс/Markdown fence при условии, что первый значимый `{` — начало нужного объекта. Он намеренно не «чинит» одинарные кавычки, trailing comma и усечённый JSON. |

## Вопросы, которые источники не позволяют считать универсальными

| Вопрос | Статус |
|---|---|
| Точный HTTP status/body для неподдерживаемого `tool_choice` в Ollama | Документация отмечает field как unsupported, но не обещает конкретный response. Не проверено. |
| Современный TGI после merge #3046 | Историческое расхождение `response_format` закрыто; без номера запущенной версии нельзя утверждать, что оно сохраняется. Version-dependent. |
| `json_object` в current vLLM и SGLang | Текущий vLLM документирует `json_schema`, а SGLang — `json_schema`; совместимый json_object в точной форме из клиента первоисточником в этой выборке не подтверждён. |
| Наличие OpenAI usage на `/v1/chat/completions` LM Studio и Ollama | Отдельные источники подтверждают usage/метрики, но не дают универсального доказательства точного `usage.prompt_tokens` + `usage.completion_tokens` для всех актуальных OpenAI-wrapper версий. |
