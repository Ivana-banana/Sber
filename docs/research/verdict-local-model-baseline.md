## 2. Найденный дефект в нашем коде

Это главная практическая ценность отчёта. Manus указывает, что llama.cpp
документирует **плоскую** форму tool call — `tool_calls[].{name, arguments}` без
обёртки `function` — и что агент обязан нормализовать обе формы. Мы этого не
делали.

`agent/llm.py`, `_read_tool_call()` принимал ровно три диалекта: OpenAI/vLLM
(`function.arguments` строкой), TGI (`tool_calls` объектом, `function.parameters`
уже разобранным) и «вызов застрял в `content`». Плоская форма проваливалась в
`return None`.

Фикс минимальный: если у элемента `tool_calls` нет словаря `function`, читаем
`name`/`arguments` с самого элемента. Существующие диалекты не тронуты, порядок
разбора прежний, `arguments`/`parameters` обрабатываются как раньше.

**Тяжесть уточнена прогоном, а не тестом.** Юнит-тест упал жёстко —
`LlmError(reason='empty content at style text')`, спуск по всей лестнице до текста, —
но это артефакт заглушки, которая отдавала плоскую форму на каждой ступени; настоящий
сервер так себя не ведёт. Реальная цена измерена прогоном настоящего `run.sh` внутри
целевого образа против заглушки в режиме `flat` (новый режим
`scripts/live_run/stub_endpoint.py`), с фиксом и без:

| | Запросы | Ступени в логе заглушки | Итог |
|---|---|---|---|
| с фиксом | 4 на 4 шага | все `shape=tools` | `solved=True stop=verified`, `tokens=500` |
| без фикса | 4 на 3 шага | `#1 tools`, далее `json_schema` | `solved=True stop=verified`, `tokens=378` |

То есть дефект не убивал прогон: он тратил один запрос впустую и **молча сбрасывал
клиент с native tools на весь остаток задачи**. Это по-прежнему стоит фикса — native
tools самая надёжная ступень и по M3, и по M22, а деградация липкая, — но
формулировка «каждый шаг тратил бы четыре запроса и всё равно падал» была завышением
и здесь исправлена.

Проверка: `pytest -q` — 247 passed / 14 skipped (Windows), 261 passed (WSL2).
Тест `test_the_llama_cpp_flat_tool_call_shape_is_accepted` падает без фикса и
проходит с ним. Контейнерный прогон: образ `sha256:1324d7bb…c8a3`, `--network none`,
`exit=0`, `post-run check: PASS`.

## 3. Что принято

1. **Рекомендация стека** — Qwen2.5-Coder-7B-Instruct GGUF Q4_K_M на llama.cpp
   `v0.3.0`, пин по commit SHA, `--jinja`, `--ctx-size 4096`, `--temp 0`.
   Пошаговые команды принимаются как есть: все флаги сверены с README того же
   коммита.
2. **Лестница по серверам** — llama.cpp даёт native tools; на vLLM и Ollama
   automatic tools не засчитывать без прогона; `tool_choice` на Ollama
   отсутствует; `strict: true` не подтверждён нигде и на vLLM явно no-op. Это
   ложится ровно на нашу липкую деградацию протокола и подтверждает решение из
   `083ac88` не слать `tool_choice`.
3. **Разделение метрик** — protocol pass rate по каждой ступени отдельно от
   semantic tool correctness, без усреднения. Принято как форма записи baseline в
   `docs/experiments.md`: server-side grammar поднимает первую, почти не трогая
   вторую, и одно число скрыло бы это.
4. **Раздел о непереносимости** — принят целиком. Ключевое: из такого прогона
   переносятся только свойства **обвязки** (агент не зависит от одной формы
   `tool_calls`, различает «поле принято» и «схема соблюдена», идёт
   `tools → json_schema → json_object → text`, валидирует аргументы локально), но
   не качество скрытой модели.

## 4. Что отклонено или отложено

1. **Выбор модели как решение** — не отклонён, но и не принят: по приёмке M22 это
   решение команды. Отчёт даёт основания, строка в `HANDOFF.md` ждёт владельца с
   GPU.
2. **Таблица vLLM** — принята только под версией `0.19.1` (см. §1).
3. **xLAM-2-3b-fc-r** — согласны с самим отчётом: это специализированный
   function-calling probe, систематически оптимистичный представитель скрытой
   general-purpose модели. Как основной baseline не берём.
4. **Оценки «качество tool use»** в таблице моделей — это инженерная калибровка
   автора, а не измерение. В `docs/experiments.md` не переносим.

## 5. Что меняется

- `agent/llm.py` — принят четвёртый диалект tool call (§2).
- `tests/test_llm.py` — воспроизводящий тест на плоскую форму.
- `HANDOFF.md` — блокер «нет endpoint» переформулирован: он больше не «нечем
  измерить», а «нужна машина с GPU и один прогон по §3 отчёта».

## 6. Границы этой проверки

- Команды сборки (§1–§2 отчёта) **выполнены**: `llama.cpp` собран на пинованном
  коммите в CPU-варианте, `llama-server --version` совпал с ожидаемым коммитом.
  Команда запуска сервера (§3) с рекомендованной 7B-моделью **не выполнялась**: у
  машины 7.8 GiB RAM, из них 5 GiB доступно WSL2, а весов 4.68 GiB — не помещается.
  Постановка передана в `TEAMMATE.md` §1.
- Фикс `_read_tool_call` проверен только против синтетического ответа в тесте.
  Против настоящего llama-server ни разу не запускался: форма взята из
  документации коммита `c1d0e7a…`, а документация может отставать от кода. Фикс
  безопасен в обе стороны — он ничего не отнимает у трёх прежних диалектов, — но
  «llama.cpp работает» из него не следует.
- Размеры GGUF и требования к VRAM проверены только для 7B. Классы «8/12–16/24 ГБ»
  — оценка автора с заявленным запасом, не измерение.
