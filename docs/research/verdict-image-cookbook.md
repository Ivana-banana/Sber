# Разбор выгрузки Manus M16: командный cookbook под инвентарь образа

Дата: 26.08.2026. Исходник — `image-cookbook.md` (запрос M16 из
`docs/prompts/manus-prompts.md`). Этот файл отвечает на один вопрос: что мы
принимаем, что отклоняем и что меняется в коде и планах.

**Итог: отчёт отклонён как cookbook.** Приёмка M16 требовала команды из утилит
образа; вместо этого поставлена одна новая утилита — `cookbook_runner.py`, 1021
строка, — и 70 «команд» вида `python3 /app/cookbook_runner.py <action>`. Принимаются
только разделы «Команды-ловушки» и разбор `sqlite3`/`gdb`/`nmap`/`tshark` как
доводы, а не как код.

Сырой архив Manus не коммитится, checksums:

| Файл | SHA-256 |
|---|---|
| `Создание командного cookbook из playbooks в Debian 12.zip` | `82804de2c8402e6fc2d6a614960a11b3f413c4da6389e4f833fe6b72ad7ca1eb` |
| `cookbook_runner.py` (внутри архива) | `f81505e2880c646f40c0f4274c88312fc976849814c3e9e7641e396317db85f8` |

Три из семи файлов архива (`playbooks-draft.md`, `submission-execution-check.md`,
`target-image-manifest.md`) — побайтово наши же вложения, проверено `diff`.

## 1. Формальное несоответствие приёмке

Приёмка M16: «Отклонить, если встречается хотя бы одна утилита вне списка».
В списке утилит образа `cookbook_runner.py` нет и быть не может: это файл, который
поставляем мы. Он не входит и в submission — значит, каждая команда cookbook'а
требует, чтобы мы добавили в архив 55 КБ нового кода со своей семантикой статусов,
своим форматом JSON и своими лимитами, до всякой абляции.

Это прямо противоречит `CLAUDE.md`: «не пишем собственный парсер, поиск или patch
engine, если в образе уже есть надёжный инструмент», «мультиагентность, RAG,
собственный фреймворк … добавляются только после абляции». Cookbook, который
нельзя выполнить, не приняв заранее чужой фреймворк, — не cookbook.

## 2. Проверка исполнением

Прогон: WSL2 `ozon`, CPython 3.10.12, наши фикстуры из `local_task_extra/tasks/`,
скопированные в `/app` ровно так, как их кладёт `Dockerfile` фикстуры
(`WORKDIR /app`, `COPY . /app`). Все команды — как напечатаны в отчёте.

### 2.1. Forensics-плейбук мёртв на 2 из 3 наших форензик-фикстур

Runner жёстко требует `/app/evidence/`:

```
forensics-manifest      rc=11 {"status":"MISSING_INPUT","required":"/app/evidence/ containing at least one regular file"}
forensics-artifact-map  rc=11 {"status":"MISSING_INPUT","required":"/app/evidence/"}
forensics-time-map      rc=11 …   forensics-events rc=11 …   forensics-iocs rc=11 …
```

Это `forensics-ssh-bruteforce`, где улики лежат в `/app/case`, потому что так
написано в инструкции задачи. У `forensics-sharded-exfil` — `/app/shards`. Каталог
`evidence/` есть только у `forensics-webshell-chain`. Имя каталога задаёт автор
задачи, а не мы; 19 шагов из 70 отваливаются на выборе имени.

Тот же класс дефекта — `ROOT = Path('/app')` и `main()` с ранним выходом
`'/app is not a directory'`. `CLAUDE.md`: «Все пути вычисляются относительно
рабочего каталога/скрипта». Здесь путь вкомпилирован в 70 команд и в текст отчёта.

### 2.2. Там, где playbook запускается, он не даёт нового знания

Тот же кейс, каталог переименован в `/app/evidence`, все шаги `OK`:

| Что | Байт |
|---|---:|
| Улики целиком (`auth.log` + `context.txt`) | 442 |
| `/app/.cookbook/` после девяти шагов | 5073 |

Содержимое `forensics-events.json` на четырёхстрочном `auth.log`:

```json
{"action": "2026-06-04T10:01:04.120Z sshd[11]: Failed password for invalid user backup from 198.51.100.44 port 51001",
 "raw":    "2026-06-04T10:01:04.120Z sshd[11]: Failed password for invalid user backup from 198.51.100.44 port 51001",
 "subject": "unknown", "object": "198.51.100.44", "artifact": "auth.log", "line": 1}
```

`action` — это вся строка, `raw` — она же второй раз, `subject` — `unknown` на всех
четырёх событиях. Задача требует назвать `compromised_user`; именно это поле
экстрактор не заполняет ни разу. `forensics-timeline.json` побайтово равен
`forensics-events.json` (`cmp` — identical): шаг 9 не делает ничего.
`forensics-conclusion.json` — константная фраза с `evidence: []`.

Обещание отчёта «подробные данные не попадают в контекст модели» верно только для
stdout. Модель всё равно обязана прочитать JSON, чтобы ответить, а JSON в 11 раз
больше исходных улик и содержит каждую строку дважды. По токенам это хуже, чем
`cat /app/case/auth.log`.

### 2.3. Audit-плейбук пуст на audit-фикстуре

`audit-hardcoded-token`, весь смысл которой — `RELAY_API_TOKEN = "sk_live_…"`:

```
audit-component-map rc=0  files=2
audit-source-map    rc=10 EMPTY   audit-sink-map rc=10 EMPTY
audit-chains        rc=10 EMPTY   audit-read-queue rc=10 EMPTY
audit-line-evidence rc=10 EMPTY   audit-gaps rc=10 EMPTY
audit-report        rc=10 EMPTY findings=0
```

Причина в коде: таблица отчёта обещает на шаге 3 «SQL, shell, file, URL, template,
auth **и secrets** sinks», а регулярное выражение `action_audit_sink_map` —
`subprocess.|os.system|shell=True|execute\(|…|eval\(|exec\(` — секретов не ищет
вовсе. Документация шире кода; это ровно тот «тихий успех», который `CLAUDE.md`
запрещает («LLM fail silently»).

`audit-chains` при этом называет «цепочкой» совпадение source- и sink-паттерна
**в одном файле**, ранжируя по числу строк. Это `rg` с лишними шагами и без
data flow.

### 2.4. Guard на подмену проверки в нашей среде вакуумный

`fix-zip-slip-extract`, слои задачи разложены как в Harbor:

```
fix-baseline  rc=0 files=1 git_returncode=128
fix-freeze    rc=0 protected=0   fix-frozen.json == {}
fix-guard     rc=0 protected=0
```

`tests/` фикстуры монтирует верификатор, агенту они не видны. «Заморозить tests и
evaluator» замораживает пустое множество, а `fix-guard` рапортует `OK`. Проверка,
которая всегда зелёная, хуже отсутствующей.

### 2.5. Что в отчёте подтвердилось

- `replacement-tshark` действительно проверяет magic classic pcap и честно отдаёт
  `MISSING_INPUT` на pcapng — заявление в таблице замен верно (прогон на их же
  `make_replacement_fixtures.py`: `rc=0 pcaps=1`, разобранный кадр с SHA-256).
- `replacement-sqlite` открывает БД в режиме `mode=ro` через URI и не исполняет
  произвольный SQL — заявление верно (`rc=0 databases=1`).
- Раздел «Команды-ловушки» фактически верен и совпадает с нашими собственными
  наблюдениями из `g6-container-run.md` (нет сети, `/proc` не смонтирован в
  chroot, syslog-время без года и offset, `git status` даёт 128 вне репозитория).

Приложенный к архиву `replacement-tshark.json` при этом содержит
`"error": "too many values to unpack (expected 6)"` — вывод более старой, сломанной
сборки runner'а. Текущий код распаковывает 7 полей и отрабатывает. То есть как
доказательство фразы «positively tested on classic-PCAP fixtures» приложен
артефакт неудачного прогона. Второй раз подряд (после `validate_playbooks.py` в
M4) приложенные Manus скрипты и их выводы расходятся с приложенным текстом.

## 3. Что принято

1. **Таблица команд-ловушек** — принята целиком как содержание для playbook'ов и
   как список того, что агент не должен пытаться делать. Кода не меняет.
2. **Разбор четырёх отсутствующих утилит** — принят как рассуждение: что теряется
   без `sqlite3`/`gdb`/`nmap`/`tshark` и чем это замещается из stdlib. Границы
   названы честно (статический дизассемблер не доказывает исполнение; отсутствие
   ответа на порту не доказывает отсутствия сервиса).
3. **Три конкретных наблюдения о среде** — вход в будущие playbook'и: улики
   лежат под именем, которое задаёт автор задачи; `tests/` агенту не видны;
   `/app` — каталог задачи, а не CWD процесса (CWD — `/opt/harbor/local-agent`,
   см. `harbor-launch-contract.md`).

## 4. Что отклонено

1. **`cookbook_runner.py` в submission** — отклонён. Причины: утилита вне списка
   приёмки; хардкод `/app` и `/app/evidence`; 19 из 70 шагов нерабочих на наших же
   фикстурах; audit-плейбук пуст на audit-задаче; документация шире кода;
   guard подмены проверки вакуумный; 55 КБ кода без единого теста в нашем сьюте.
2. **70 команд как cookbook** — отклонены: они не команды образа, а вызовы п. 1.
3. **Сканирование `127.0.0.1:1–1024`** — отклонено отдельно, даже если бы код
   принимался. Проверено по публичному репозиторию на `71f9081`: единственная
   публичная задача с сервисом, `fix-sqli-login`, поднимает `uvicorn … --host
   127.0.0.1 --port 8000` и опрашивает `http://127.0.0.1:8000/healthz` — то есть
   порт вне диапазона 1–1024, и сервис стартует **в верификаторе, после** фазы
   агента. Скан во время работы агента не увидит его ни по диапазону, ни по
   времени, но потратит 1024 connect-попытки в 128 потоках под нашим
   600-секундным потолком.

## 5. Что меняется

Ничего в `agent/`. M16 остаётся незакрытым: у нас по-прежнему нет командного
cookbook'а. Переформулировка запроса — в `docs/prompts/manus-prompts.md`, строка
M16: следующий заход обязан давать команды **из утилит образа**, по одной на шаг,
и явно запрещать поставку собственного исполняемого файла.

## 6. Границы этой проверки

- Прогон выполнялся в WSL2 на CPython 3.10.12, не в целевом образе на 3.12.
  Расхождение версии не влияет на разобранные дефекты: они в путях, регулярных
  выражениях и логике, а не в API интерпретатора.
- Проверены 4 фикстуры из 18 (`forensics-ssh-bruteforce`, `audit-hardcoded-token`,
  `fix-zip-slip-extract` и синтетические фикстуры Manus). Полный прогон 70 шагов
  на всех 18 задачах не делался: найденных дефектов достаточно для отказа.
- Разделы, принятые в п. 3, приняты как **рассуждение**. Их полезность в prompt не
  измерена; до абляции это черновик, а не решение.
