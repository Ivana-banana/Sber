# Дизайн F4 — снять 90-с pre-checkpoint clamp с LLM-вызова (на ревью, до кода)

Спроектировано 14.09 в коопе. Реализация — после дизайн-ревью ai-challenge-cc.
`agent/state.py` (Budget) → tool/budget policy: человек + парный замер до кандидата.
Основание: L-Q3-FIX показал, что один raised thinking-вызов на 30b ≈ 90 с и режется
именно этим clamp'ом (find-sqli plan 90.065, fix-sqli 90.013), а не max_tokens.

## Что сейчас (дефект)
`Budget.llm_timeout_s()`:
```
ceiling = min(LLM_TIMEOUT_S(120), spendable_s())
if not past_early_deadline():                      # < 90 с ИЛИ < 40% шагов
    ceiling = min(ceiling, early_deadline_s - elapsed_s())   # ← F4 clamp
return max(0, ceiling)
```
До раннего чекпоинта (early_deadline_s=90 с) вызов зажат до `90 − elapsed`. На шаге 1
(elapsed≈0) это ~90 с. Thinking-вызов, которому нужно >90 с, обрывается по времени →
finish=length ИЛИ пустой ответ без payload → по #1 «lower bound», по #2 retry-raise. То
есть F4 усугубляется #2: чем длиннее thinking, тем вернее обрыв.

## Что снимается
Строку `if not past_early_deadline(): ceiling = min(ceiling, early_deadline_s - elapsed_s())`.
Новый потолок: `min(LLM_TIMEOUT_S, spendable_s())`. Чекпоинт остаётся ПОДСКАЗКОЙ
(«запиши лучший вариант сейчас», loop.py past_early_deadline), а не убийцей вызова.

## Формула потолка (детали для ревью)
- `spendable_s() = remaining_s() − verify_reserve_s` (резерв на verify уже учтён).
- `remaining_s()` учитывает deadline задачи (total_s − elapsed).
- Значит вызов не залезет в verify-резерв и не переживёт deadline — эти границы держатся
  и без clamp'а. Убирается ТОЛЬКО искусственный зажим 90-с чекпоинтом.

## Trade-off и почему нужен парный замер на 7B
Зачем clamp был: на 120-с задаче с НЕзаявленным раннером-таймаутом он гарантировал, что
deliverable появится к 90 с, а не после одного 120-с вызова. Убрав clamp, на короткой
задаче один вызов может идти до min(120, spendable) → на 120-с задаче killed без файла.
Три варианта, решает ревью:
- **(A, рекомендую)** снимать clamp ТОЛЬКО когда клиент детектировал thinking-эндпоинт:
  非-thinking (7B) сохраняет гарантию 90 с, thinking получает полный бюджет. Минус:
  связь Budget↔HttpLlm (нужен сигнал `client._thinking_endpoint` в state или флаг в loop
  после первого thinking-ответа). Реализуемо: loop уже видит reply; выставить
  `state.budget.allow_long_llm = True` при первом thinking-признаке.
- (B) поднять early_deadline_s для thinking (тот же сигнал, мягче).
- (C) снять clamp всегда, но гарантировать ранний placeholder-deliverable ДО первого
  длинного вызова (loop пишет пустой валидный результат на шаге 1). Меняет loop, не budget.
Общий принцип: не потерять «deliverable к дедлайну» на 7B ради thinking.

## Парный замер (шлюзы)
- 30b, тот же архив ± F4: ожидание — раньше обрезанные 90-с вызовы завершаются, меньше
  «lower bound»-пометок, возможно +0..1 solved (find-sqli уже 1; fix-sqli-login мог бы
  дописать верную правку, если время было потолком). Токены могут вырасти (полный thinking
  считается) — это честнее, не регресс по solved.
- **7B, тот же архив ± F4: КРИТИЧНО — solved и deliverable-count НЕ должны упасть.** 7B без
  thinking: если вариант (A), поведение байт-в-байт прежнее (clamp остаётся). Тест на это.
- Критерий: solved не потерян ни на одной модели; на 30b «lower bound»-пометок меньше или
  0; ни один вызов не killed раннером из-за отсутствия раннего deliverable на 7B.

## Не менять
LLM_TIMEOUT_S (120) — жёсткий потолок одного вызова, держится. verify-резерв. Ранний
чекпоинт-подсказку в loop (она полезна и остаётся). Sampling, playbooks.
