# live-runs — сырые таблицы прогонов против настоящей модели

Одна строка на задачу, ровно то, что напечатал `scripts/eval/run_suite.py`. Лежат в
репозитории, потому что карточки в `docs/experiments.md` ссылаются на эти числа, а
проверить утверждение по пересказу нельзя. Файлы маленькие (~1 КБ), тяжёлые логи и
трассы сюда не едут — они воспроизводятся командой из карточки.

| Файл | Прогон | Изменённый фактор | Решено |
|---|---|---|---:|

| `E012-results.tsv` | политика путей | workspace по тексту задачи + запись по названным путям | 3/18 |
| `E013-results.tsv` | застревание → производство | **откачено**: 0 прироста, +23% токенов | 3/18 |
| `E014-partial-results.tsv` | конверт ответа | **прогон оборван** на 5-й задаче из 18 | — |
| `E014-control-results.tsv` | текущий paired control | точный архив E012 (`617b774`) в той же среде, что полный E014 | 3/18 |

Колонки: `reward` — вердикт верификатора самой задачи (`/logs/verifier/reward.txt`),
единственное, что считается результатом; `tokens` — то, что агент сообщил о себе сам
(`?`, если его убили раньше); `ep_tokens`/`ep_calls` — независимый счётчик на endpoint;
`claim` — что агент сам думал о своём результате. Расхождение `claim=True` при
`reward=0` — это класс `verification`, самый дорогой: прогон остановился, считая себя
готовым.

`E014-partial-results.tsv` — не результат, а сохранённая улика. Прогон убит вместе с
контейнерами модели и прокси после 5 из 18 задач, ни одна из трёх решаемых E012 задач в
этот префикс не попала, поэтому решаемость по нему не считается вообще. Что в нём видно:
при `temperature 0` три из пяти строк совпали с E012 до токена, а `ctf-header-override`
перестал быть ложной победой (`claim=True, reward=0`) и честно упёрся в `stuck`. Полный
прогон фактора повторён 02.09; его paired control и treatment лежат рядом.

У E014 два baseline. Исторический E012 нужен для хронологии, но не является строгим
control для сентябрьского прогона: mutable base image сдвинулся, а прежний model alias
не сохранился с manifest digest. Поэтому `E014-control-results.tsv` собран из точного
архива E012 и прогнан сразу после treatment на том же endpoint и уже кэшированных
образах. Эта пара меняет только 27 строк `agent/loop.py`. Treatment не прошёл gate:
2/18 против 3/18, 0 приобретено, 1 потеряно, +6097 токенов и +299 секунд.

Два повтора `mut-audit-query-gate` дали 1 и 0 даже при `temperature=0`; вместе с
расхождением старого и нового control это запрещает выдавать единичную потерю за
устойчивую причинную оценку. Инженерный gate всё равно красный: доказательства прироста
нет, а наблюдаемая paired строка содержит регрессию.

Модель прогонов — `qwen2.5-coder:7b` на CPU. Это **не** модель оценки, и ни одно число
отсюда не переносится на закрытый набор; ограничения перечислены в карточках.

E015 использует тот же модельный файл `qwen2.5-coder:7b-instruct-q4_K_M`, но не task
image: локальный `python:3.12-slim` в сети только с моделью. Поэтому это измерение
непрямой инъекции, а не доказательство совместимости с `secureintelligent/acp`.
`marker_created=True` означает реальный запрещённый side effect; `inputs_changed=False`
во всех строках означает, что fixture data остались прежними. Endpoint counter отбросил
один поздний ответ, поэтому его token sum — нижняя граница.

E017 — не новый single-factor treatment, а свежий baseline фактического кандидата после
обычного revert проигравшего E014. Он решил 4/18: три ранее уже решавшиеся задачи и
`ctf-header-override`; при этом `mut-audit-query-gate` снова оказался вариативным и в
этот раз дал 1. Полный environment/image ledger и причины каждого нуля лежат рядом в
`E017-summary.txt`; тяжёлые trace остаются в ignored `build/`.

Для E018 phase/action traces намеренно тоже закоммичены: это небольшой первичный
результат observability, без которого вывод о timeout нельзя перепроверить. В двух
attempts завершённые `plan` заняли 89.990/89.988 из 95.1 s, `act` — меньше 0.02 s,
`verify` не начался, а последняя незакрытая фаза снова `plan`. Значит ближайшая
абляция не должна менять `MAX_STEPS`, reserve или recovery: они не успели сработать.
Вторая попытка использовала уже запущенный model container, но один повтор и
post-run-only task image ID не доказывают ни causal warming effect, ни identity image.
