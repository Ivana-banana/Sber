The later-call median is what decides this run. Every call after the first re-sends a
prefix the server already holds, and the system block sits in front of the observation
history under both orders, so a second call's prefix is byte-identical whichever order
build_system() used. Block order cannot move it. It moved by +14%, and thirteen earlier
runs held it inside a one-second band. The stand was slower for those 44 minutes, and
the first call was measured through that slowdown.

Bench numbers that motivated the factor, measured 04.09 before the run:
  prefill ~29 ms per uncached token, decode 6.2 tok/s, repeat of the same prompt 0.7 s,
  shared prefix + new tail 11.3 s vs 34.5 s cold, no shared prefix 30.2 s,
  current order on neighbouring tasks 22.1 s, proposed order 14.1 s.
They did not transfer to the suite. Between the first call of task A and the first call
of task B the suite issues ~8 long calls of task A; the bench issued none. The obvious
suspect is eviction of the shared prefix, and it is a bench question, not another suite
run.

New false win, a fifth form: mut-greeting-farewell wrote the literal text "4361696f"
into the marker (hex for Ciao, as text) and offered

  cat /srv/bootstrap/farewell.marker | od -A x -t x1z -v

Every stage of that pipeline is a reader or a formatter, so the pipeline exits 0 for any
content. _cannot_fail lets it through by design: it allows anything containing a pipe,
because every real check the loop has seen contained one and refusing a real check costs
the task outright. The tightening that keeps that reasoning is "a pipeline whose every
stage is a reader and which contains no comparator", not "no pipes". Not implemented --
the human's stated priority is the timeout class.

Review corrections (critic pass, 13:25):
  - "later calls" mixes two mechanisms. Up to step 8 a call is a strict extension of
    the previous request; from step 9 the observation window slides and it costs three
    times as much. The clean stand-speed reading is steps 2-6: 7.5 s -> 8.1 s, +8%.
    The slowdown is real, it is 8% and not 14%.
  - In all 36 task runs of E033 and E034 the first reply arrives as
    {"name": ..., "arguments": {...}} in content, not as a native tool call, so the
    native_tools rung fails on every task and the first step pays an extra full
    prefill. Untested by any experiment so far.
  - The 172 -> 153 fall in calls is partly behavioural: mut-greeting-farewell took 10
    steps in E033 and 2 in E034.
  - time to first write is computed over 13 tasks in E033 and 14 in E034.

Prefix eviction, tested 04.09 13:35-14:00 (scripts/eval/bench_prefix.py, 364-token
resident block):

  cold        12.2 s   a resident block the server has not seen
  repeat       3.0 s   the identical request again
  adjacent     4.3 s   same block, new tail, nothing in between
  worked       4.2 s   same block, new tail, after 8 calls of a task

So the shared prefix survives a task's worth of work: `worked` sits on `adjacent`, not
on `cold`. Eviction is not why E034 showed nothing in the suite, and the guess written
into the card before this measurement was wrong.

What is left is the noise floor. The normalised first call (first / median of steps
2-6) is 5.23, 6.01 and 5.14 across E033, E034 and E035, and the last two are the same
archive -- a spread of 0.9, about 17%. A reorder that moves the shared prefix from 362
to about 630 tokens can be worth roughly 20% of the first call, which is inside that
band. E034 did not fail to reproduce; a single suite run cannot resolve it.
