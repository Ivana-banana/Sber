# `find-sqli-login`: правильная находка уничтожена невалидным JSON

Прогон `build/public-20260912-E-BASE-r1`, архив
`133b81d09b0dc38be986ec85eceacb35809672da63828a31a4478e450decf53c`,
модель `qwen2.5-coder:7b-instruct-q4_K_M`, GPU-стенд `claude-e-model-20260912`.
Строка: `reward=0 tokens=71758 wall=306.4s stop=steps failure=reasoning`.

## Что произошло

На шаге 9 модель записала в `/app/security_report.json` содержательную находку:
SQL-инъекция в `/app/routers/auth.py:17`, evidence — сама строка с f-string,
impact — инъекция через `username`/`password`.

По трём gate-ам официального verifier
(`local_task/find-sqli-login/tests/test_security_report.py`) этот текст проходит:

| gate | сигнал в тексте |
|---|---|
| `sql_injection_signals` | `sql injection`, `f-string`, `parameterized` |
| `login_signals` | `routers/auth.py` |
| `detail_signals` | `req.username`, `req.password`, `password` |

Но файл **не является валидным JSON**. В строке `evidence` осталась
неэкранированная кавычка, и разбор падает на `Expecting ',' delimiter: line 1
column 309`. Воспроизведение:

```sh
python3 - <<'PY'
import json
from pathlib import Path
t = Path("build/public-20260912-E-BASE-r1/logs/find-sqli-login.r1.trace").read_text(errors="replace")
action = json.loads(t.split("--- call 9 ---")[1].split("--- call 10 ---")[0].strip())
json.loads(action["content"])
PY
```

`write_file` вернул `ok` и `wrote N bytes`. Про то, что документ не разбирается,
агент не узнал ниоткуда: ни инструмент, ни verify-фаза этого не проверяют.

Дальше модель «чинила» результат тем, что записала `{"findings": []}` —
валидный, но пустой документ — и повторила ровно эту запись **двадцать раз
подряд**, до исчерпания 30 шагов. Итог: 71 758 токенов, ноль, и на диске пустой
отчёт вместо уже готовой правильной находки.

## Механизм, а не единичная неудача

Разделяются два дефекта.

1. **Молчаливый успех при нарушенном формате.** Инструкция требует
   machine-readable JSON; инструмент подтверждает запись по числу байт. Это
   прямо противоречит правилу проекта «ошибка внешнего инструмента не должна
   молча превращаться в успех». Модель не может исправить ошибку, которую ей не
   показали.
2. **Потеря уже полученного результата.** Пустой валидный документ вытеснил
   непустой невалидный, и повтор идентичной записи не был остановлен.

Ночной прогон `build/public-20260912-night-exact-full-r1` промахнулся по-другому
и мимо тех же gate-ов: там JSON был валиден, но `evidence` содержал пересказ
(«f-string concatenation for SQL query»), и не сработал только
`detail_signals`. То есть обе неудачи — про качество поля `evidence`, а не про
понимание уязвимости: модель находит дефект и в том, и в другом прогоне.

## Предлагаемые факторы (по одному за прогон)

- **C1.** `write_file` в машиночитаемый формат проверяет разбор записанного и
  возвращает точную ошибку разбора в наблюдении. Файл всё равно пишется —
  дедлайновый чекпойнт требует, чтобы результат существовал; меняется только то,
  что агент видит. Это не оракул содержания: про findings не утверждается ничего.
- **A1.** В `CODE_AUDIT` playbook закрепить то, что сейчас говорится только в
  дедлайновом чекпойнте: evidence — процитированная строка кода, а не пересказ,
  и impact называет, что получает атакующий. Замер: +13 Qwen-токенов
  (226 → 239 при бюджете 400).

Ожидание до прогона: C1 должен убрать двадцать одинаковых записей и дать модели
шанс исправить экранирование; A1 бьёт в ночной режим отказа. Проверять их
раздельно, control — этот прогон.

## Границы

Оба фактора проверены пока только чтением сырых логов. Ни один не измерен живым
прогоном; solved count по ним не заявляется. Успех на `find-sqli-login` ничего не
скажет о закрытом наборе — это один публичный кейс.
