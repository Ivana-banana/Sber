# Офлайн-cookbook для Debian 12: `code-audit`, `code-fix`, `forensics` и `ctf`

## Рамки исполнения

Этот cookbook рассчитан на **Debian 12 (amd64), root, `WORKDIR=/app`, без сети** и использует только CPython 3.12 со стандартной библиотекой и проверенные утилиты целевого образа. Основание для этого набора — предоставленные `target-image-manifest.md` и `submission-execution-check.md`: в частности, там подтверждены отсутствие `sqlite3`, `gdb`, `nmap`, `tshark`, отсутствие смонтированного `/proc` в проверочном запуске и отсутствие сети.

Все приведённые ниже команды предполагают, что вложенный файл **`cookbook_runner.py` уже размещён строго по пути `/app/cookbook_runner.py`**. Это не шаблон пути: это фиксированный путь cookbook. Сам runner использует только стандартную библиотеку Python 3.12 и запускает из образа лишь `git`, `patch`, `file`, `readelf`, `objdump` и `strings`. Он сохраняет развёрнутые результаты в `/app/.cookbook/`, а в stdout выдаёт **ровно один JSON-объект**, не более **1 400 байт**. Поэтому подробные данные не попадают в контекст модели.

> **Протокол статусов.** Успех — `"status":"OK"` и exit code `0`. Нормальный пустой результат — `"status":"EMPTY"` и code `10`: это не ошибка команды. Необходимый локальный вход отсутствует — `"status":"MISSING_INPUT"` и code `11`. Ошибка разбора, исполнения или превышения срока — `"status":"ERROR"` и code `2`. Значит, отсутствие находок всегда отличимо от ошибки и от отсутствующего входа.

Каждая команда включает `--timeout`. В CPython под Linux этот лимит принудительно обеспечивается `signal.alarm`; допустимый диапазон runner — 1–600 секунд. Внутренние лимиты runner: не более 1 200 файлов, не более 2 MiB на читаемый текстовый/артефактный файл, не более 8 KiB вывода каждого дочернего процесса, 2 000 событий и 2 000 IOC, 1 000 пакетов PCAP и 20 ELF/SQLite/PCAP объектов. Столбец «Вывод» задаёт верхнюю оценку **stdout**, а не размера сохраняемого JSON-доказательства.

## Команды-ловушки в этом образе

Ниже перечислены команды, которые синтаксически выглядят привычно, но здесь могут породить ложный вывод. Их не следует использовать как доказательство без дополнительной локальной проверки.

| Команда-ловушка | Почему вывод ложный или неинтерпретируемый в данной среде | Безопасная трактовка |
|---|---|---|
| `curl -fsS https://example.com/` | Проверочные прогоны выполнялись в отдельном network namespace без сети. Ошибка DNS/route/connect сообщает об изоляции контейнера, а не о доступности `example.com` или его TLS-конфигурации. | Считать только тестом изоляции; не использовать для внешней верификации. |
| `wget -qO- https://example.com/` | Та же зависимость от отсутствующей сети; `-q` ещё и скрывает диагностический контекст. | Не применять для evidence; не заменять им local artifact verification. |
| `nc -vz 198.51.100.7 443` | Отрицательный connect отражает network namespace/маршрутизацию, не состояние удалённого порта. | Проверять лишь строго loopback service в рамках CTF-cookbook. |
| `openssl s_client -connect example.com:443` | Не отличает отсутствие сети, DNS, route и сервера; может ждать ввода/EOF в интерактивном режиме. | Не делать вывод о сертификате или TLS endpoint. |
| `tcpdump -i any -c 10` | В изолированном namespace может не быть полезного интерфейса/трафика; отсутствие пакетов не доказывает отсутствия сетевой активности за пределами namespace. Также capture зависит от container capabilities. | Анализировать предоставленный capture file; не использовать live capture как общесистемное доказательство. |
| `journalctl -n 100` | В образе/проверочном chroot не гарантированы systemd и journal runtime. Даже наличие binary не создаёт журнал. | Сначала фиксировать наличие артефактов; `forensics-no-journal-assumption` намеренно считает сервисную пригодность ложной. |
| `systemctl status ssh` | Контейнер обычно не запущен с systemd как PID 1; вывод «not booted with systemd» не говорит, запущен ли процесс на исходном хосте. | Не использовать для process/service attribution. |
| `ps aux` | В проверенной ФС `/proc` не смонтирован: `ps` завершался с диагностикой о необходимости mount `/proc`. | Считать это ограничением chroot, а не доказательством отсутствия процессов. |
| `ss -lntp` | Без полноценного `/proc`/net namespace может показать только namespace-локальную картину или не показать владельцев PID. | Использовать исключительно как auxiliary snapshot текущего namespace, не как карту хоста. |
| `nmap -sV 127.0.0.1` | Сам бинарник `nmap` отсутствует. Установка запрещена, поэтому нельзя подменять этот шаг «похожим» недоступным вызовом. | Использовать `replacement-nmap`, понимая его ограниченный TCP-loopback scope. |
| `tshark -r /app/evidence/capture.pcap` | Бинарник `tshark` отсутствует. Даже если был бы, путь может не содержать capture. | Использовать `replacement-tshark` только для classic PCAP; pcapng явно обозначать неподдержанным. |
| `sqlite3 /app/evidence/data.db '.tables'` | CLI `sqlite3` отсутствует, хотя модуль Python `sqlite3` в CPython присутствует. Ошибка command-not-found не означает, что DB нельзя прочитать. | Использовать read-only `replacement-sqlite`. |
| `gdb /app/challenge` | `gdb` отсутствует; отсутствие отладчика — не свойство бинарника и не свидетельство защит. | Использовать статический `replacement-gdb`; не приписывать ему runtime-свойства. |
| `git log -1 --format=%ci` | В `/app` может отсутствовать `.git`; результат относится к распакованному workspace, не к происхождению исходников. | Использовать только если manifest/baseline явно показывает git repository. |
| `git status --porcelain=v1` | В негитовом каталоге дает code 128. Это не означает dirty/clean state, а означает «не repository». | В `fix-baseline` код хранится как поле, а source hashes всё равно снимаются. |
| `readelf -h /app/something` | Если файла нет или это не ELF, ошибка описывает тип/раскладку файла, не его «безопасность». | Предварительно применять объектную классификацию; `EMPTY` для отсутствия ELF — нормальный результат. |
| `grep -i 'auth' /app/evidence/log` | `-i` зависит от locale и Unicode case-folding; `LC_ALL=en_US.UTF-8` задан в образе, но текст журналов может иметь иной язык/кодировку. Бинарные и неполные UTF-8 данные также меняют интерпретацию. | Для evidence сохранять raw line и применять ограниченные ASCII/явные regex, как делает runner. |
| `sort`/`date` по syslog-времени вида `Aug 25 12:00:00` | У такого timestamp нет года и offset; month name может зависеть от locale. Лексическая сортировка не создаёт достоверный временной порядок между артефактами. | Сохранять original и нормализовать лишь ISO-8601 с `Z`/числовым offset. |
| `find / -xdev -type f` | Обходит весь контейнер, создаёт большой/дорогой вывод и смешивает application evidence с образом/venv; в chroot mount layout не равен host layout. | Ограничиваться `/app` и `/app/evidence`; runner лимитирует число файлов и размер чтения. |
| `curl --retry 20 ...` или `wget --tries=20 ...` | Повторение недоступной сети расходует весь бюджет времени, но не добавляет доказательства. | Не ретраить off-container endpoint; сначала доказать доступность подходящего namespace. |

## Проверка совместимости и известные границы

Runner синтаксически проверен под Python 3.12 и положительно протестирован на локальных SQLite и classic-PCAP fixtures; действия `forensics` и `ctf` также smoke-tested на малом наборе артефактов. Внутри cookbook намеренно **нет** shell-пайпов, `head`, `sed`, `awk`, `find`, `timeout`, `tee`, `mkdir`, `cp` и других «обычно доступных» программ: так команды не опираются на утилиты вне заявленного набора. Также нет флагов, появившихся только в новых версиях `git`, `curl`, `rg`, `readelf`, `objdump` или Python.

Ни один статический regex/source→sink результат не является доказательством exploitability. Никакое отсутствие слушателя в loopback snapshot не является доказательством отсутствия удалённого сервиса. Ни один parser-результат без двух независимых первичных артефактов не повышается из корреляции до причинного утверждения. Именно поэтому cookbook различает `EMPTY`, `MISSING_INPUT`, `CONFLICT`, `NOT_CONFIRMED`, `FAIL` и `ERROR` вместо того, чтобы интерпретировать отсутствие stdout как успешное завершение.
