# Почему ночные прогоны не дали прироста: разбор публичных задач

Исходный HEAD: `84c5069`. Анализ 07.09.2026. Новых LLM-прогонов нет; runtime
не менялся. Цель — шлюз C из PLAN.md: настоящий reward, сначала `local_task/`.
Это исправление выводов предыдущего анализа, а не обещание непроверенных побед.

## Что установлено заново

Пересчитаны 20 таблиц, 240 task runs: 60 public и 180 дополнительных.
Стоимость: **909 536** endpoint tokens / **13 506,2 с** на public и
**2 158 171** / **42 871,7 с** на дополнительных. Всего 3 067 707 токенов;
76% суммарного task wall time потрачено на наши fixtures.

База B1/B2 — 2/6, только `hello-file` и `bye-file`. В восьми вариантах
**ни одной победы на четырёх содержательных public**: вместе с контролями 0/40.
H03 и H06b дают 1/6, остальные 2/6. Экономия H03 не проходит приоритет solved.

Главная находка — не «модель прочитала код и не поняла». Большинство вариантов
до чтения нужных данных вообще не дошло.

| Public task | Факты по десяти запускам B1, восемь плеч, B2 | Что требует организатор |
|---|---|---|
| `find-sqli-login` | 10/10 без запроса `read_range` и без shell; 9/10 первый plan упирается в 90 с; 9 сохранённых финальных отчётов содержат пустые findings | Непустой JSON-отчёт с подтверждённой SQLi в auth |
| `fix-sqli-login` | 10/10 имеют endpoint error в первых трёх сохранённых requests; ни одного чтения `routers/`; пишут README/timeout_error либо ничего | Исправление кода: bypass закрыт, штатные тесты проходят |
| `fix-sqli-search` | Ни одного чтения `routers/` и изменения исходников; основном читают entrypoint, затем пишут README | UNION не раскрывает users, обычный search и регрессия работают |
| `incident-log-forensics` | 10/10 первый plan упирается в 90 с; 8/10 совсем без запросов чтения; в двух остальных чтение неполное | Корреляция recovered app audit, proxy/XFF и всех edge shards; четыре точных поля |

Здесь запрос инструмента не равен исполнению: `.trace` содержит ответы endpoint,
в том числе опоздавшие и отклонённые. Факт исполнения подтверждаем `.log` и
tool observations в `.calls`; полные тела сохранены **только для первых трёх
запросов**. Отсутствие запроса чтения во всей trace — более сильный отрицательный
сигнал, чем наличие запроса — положительный.

## Причинная цепочка, которую предыдущая очередь пропустила

В B1 audit первый plan заканчивается за 90,135 с. Ответ endpoint с `list_dir`
попал в trace, но в следующий запрос модели приходит **endpoint TimeoutError**,
а не список файлов. Сразу следом контроллер сообщает:

> Запиши лучший вариант через write_file сейчас, улучшишь потом.

Модель начинает записывать `{"findings": []}`. Ни H01a (подписать observation),
ни H01b (номера строк), ни H09 (ошибка проверки) здесь не имеют полезного входа:
нет чтений и нет попыток `finish` в audit.

В B1 login первый plan занимает 85,731 с и успевает выдать list_dir. По реальному
`Budget.llm_timeout_s()` следующему вызову остаётся **4,269 с** до раннего
checkpoint. После TimeoutError модель создаёт файл о провале pytest, которого
не запускала. Ошибка транспорта становится выдуманной ошибкой приложения.

Offline replay текущего Budget воспроизводит одновременно:

- второй call timeout 4,269 с;
- `past_early_deadline=True` на втором шаге;
- 509,869 с до общего deadline, 389,869 с вне verifier reserve;
- необходимость записи по контроллеру при отсутствии прочитанного кода.

Это **доказанный механизм преждевременного перехода**, но пока не доказательство,
что его устранение само даст решение. H06b показывает второе ограничение:
замена подсказки на «найди недостающий факт» всё равно не довела до уязвимых
обработчиков. Удержать исследование и направить его — две отдельные задачи.

Первый plan E049 на четырёх содержательных public занимал 3,408–4,787 с;
B1/B2 — 35,771–90,135 с. Архивы различаются, поэтому приписывать разницу только
CPU/GPU, серверу или prompt нельзя. Но прежний тезис «timeout больше не мешает»
не описывает текущую ночь: внешний stop=stuck маскирует внутренний timeout.
Совпадение solved у двух контролей не доказывает равенство latency, offload и
режимов внутри всей серии. Оно подтверждает только совпадение конечных побед.

## Что исправить в интерпретации прежних гипотез

1. **Мои прежние рекомендации были слишком сосредоточены на оформлении prompt
   и наблюдений.** Сначала следовало проверить исполнение нужного механизма на
   одном public-кейсе, а затем тратить ночь на сравнительные прогоны.
2. **H06b не доказывает, что текущую раннюю запись нельзя трогать.** Его падение
   до 1/6 — потеря тривиального hello; ни база, ни H06b не решают содержательные
   задачи. Файлы README и пустые отчёты не являются прогрессом в исправлении SQLi.
3. **H05a нельзя отвергнуть по одному совпадению числа 5/18.** Относительно обоих
   ночных fixture-контролей он добавил `fix-redirect-scheme`, lost=0. E060/E061
   имели другой пятый успех — `mut-fix-session-lookup`. Это кандидат на повтор,
   не доказанная победа и не приоритет выше public. Причинный механизм также
   нужно проверить: название плеча не доказывает влияние именно на аудит.
4. **H09 не проверил полезность обратной связи при настоящем исправлении.**
   Audit/forensics вообще не вызывают finish; fix проверяет README/error files.
   Отсутствие прироста здесь не опровергает recovery после содержательного теста.
5. План D0–D3 был отложен, а дополнительные задачи прогнали у всех восьми плеч,
   хотя public-прироста не было. Получилась дорогая серия с малой информационной
   ценностью. Assisted diagnostics допустимы как работа разработчика с public
   inputs; их нельзя выдавать за автономный score или переносить ответы в runtime.

## Следующие гипотезы в порядке проверки

### N1. Потери на первом протоколе лишают агента исследовательской фазы

**Основание:** 9/10 audit и 10/10 forensic первых plan упираются в 90 с;
первые запросы используют `tools`, последующие переходят на `response_format`.
Зафиксированные ответы приходят как JSON в content. Это ещё не доказывает,
что на том же prompt вариант JSON будет быстрее — это и требуется измерить.

**Дешёвый опыт:** взять точное тело первого audit request из `.calls`, оставить
model/messages/schema/max_tokens/temperature одинаковыми; сравнить native и
JSON schema с явным учётом cold/warm и порядка AB/BA. Изменяется только оболочка
протокола. Фиксировать валидность действия и время до ответа; опоздавший ответ
не считается выполненным действием. Старый `bench_first_call.py` использует
другой prompt и cap=64, поэтому не заменяет этот replay.

**Пилот:** тем же loop выполнить public audit с экспериментально выбранной
начальной формой. Предсказание: до 90 с появляется успешное чтение исходников,
а не только write. Если вызов ускорился, но модель всё равно ничего не читает,
латентность — не достаточная причина, переходим к N3.

**Runtime-кандидат только после результата:** согласование протокола с
сохранением достижимости native-only endpoint. Не повторять отменённый E036:
глобально поставить JSON и навсегда отрезать native fallback нельзя.

### N2. Один checkpoint ошибочно служит и сроком первого файла, и timeout LLM

**Основание:** воспроизводимый переход 85,731 → 4,269 → TimeoutError → write
при оставшихся 390 с полезного времени. Это конкретнее прежнего H06b,
который менял текст следующей подсказки, сохраняя границу отмены вызова.

**Первый отдельный фактор:** на 600-секундном public-пилоте перестать обрезать
текущий LLM-вызов остатком до *мягкого* production checkpoint; оставить hard
deadline, timeout запроса и verifier reserve. Никакого увеличения MAX_STEPS.
Предсказание — чтение на втором шаге исполняется, транспортная ошибка исчезает.
Если после первого успешного чтения всё равно начинается пустой отчёт,
нужен следующий отдельный фактор: переход по наличию свидетельства и реальному
оставшемуся времени, а не только по возрасту процесса.

**Ограничение:** hello/bye имеют 120-секундный внешний лимит, который текущий
агент не знает. Изменение нельзя включать повсюду без их regression gate.
Нельзя выбирать режим по имени public task. Извлечение буквального результата
из пользовательского требования допустимо; специальные ответы для hello/bye — нет.

N1 и N2 могут взаимодействовать. После дешёвых проверок допустим квадрат
`B`, `B+N1`, `B+N2`, `B+N1+N2` на одном audit; каждая сторона меняет один фактор.
Успех комбинации не приписывать одному из факторов.

### N3. Модель не умеет выбирать следующий исходник; выбор надо поддержать кодом

**Основание:** ни одно из 30 SQLi task runs не дошло до `routers/`.
Уязвимый data flow есть в предоставленных исходниках; отсутствие доказательств
в отчёте сейчас связано прежде всего с отсутствием этих исходников в наблюдениях.

**Диагностическое разделение:** дать той же модели один релевантный исходник
из public environment и исходную инструкцию audit, без solution/tests/эталонного
отчёта. Оценить результат официальным checker снаружи. Это assisted diagnostic,
не увеличение public score. Если не проходит даже так — навигация не объясняет
всё, нужно отдельно проверять понимание кода и построение evidence.

**Автономный кандидат:** ограниченный сбор исходников по импортам/обработчикам
и местам DB/IO calls с provenance; не просто новый список имён файлов в brief.
AST читать без import/исполнения исследуемого кода, исключить venv/build,
соблюдать лимит вывода. Выбор не должен знать `auth.py`, `/login`, SQLi payloads
или названия задач. Safe parameterized code должен присутствовать как контроль.

Предсказание: модель получает уязвимый обработчик до первого кандидата;
official audit впервые проходит. Затем оба official fix и нейтральное
переименование/перенос обработчика. Если источник доступен, но verdict всё ещё
неверный, расширять индексатор бессмысленно.

### N4. Контроллер считает файл результатом даже там, где нужен изменённый код

**Основание:** все 20 official fix попыток не исправили исходники; 18 запрашивали
запись README/timeout_error, два H06b не запрашивали запись. Instruction требует
ремонта приложения. `state.artifacts` не различает результат, заметку и скрипт
проверки; любая запись открывает выход по stuck.

**Кандидат:** отделить checkpoint состояния workspace от «создать файл»:
для repair учитывать изменения production source (включая shell), показывать
короткий diff и проверять поведение; для report — требуемый артефакт. Файл
диагностики транспорта не должен переводить ремонт в состояние готового кандидата.
Это не жёсткий запрет заканчивать неуспех и не бесконечное продолжение петли.

Проверять после N3: сначала модель локализует дефект, затем применяет малую правку,
запускает доступные `pytest tests/` и собственный негативный probe из найденного
data flow. Полный official checker запускается harness снаружи; его assertions
не становятся подсказками агенту. Штатный pytest до правки может быть зелёным —
это не свидетельство отсутствия уязвимости. Признак успеха: хотя бы один из двух
official fix проходит security и regression, а README не выдаётся за исправление.

### N5. Форензике нужен исполняемый расчёт по всем источникам

**Основание:** 8/10 попыток просто выдумывают четыре поля без чтения; H06b читает
лишь primary log/note, пропуская recovered и edge shards. `check_parity.py`
организаторов проходит: public fixture согласован, данных для ответа достаточно.

После N1/N2 собрать inventory всех предоставленных файлов, затем выполнить
небольшой parser: JSONL → таблица кандидатов → join по request id с proxy/edge →
поля ответа с происхождением. Это последовательность проверяемых вычислений,
не прежний macro, генерирующий целый решатель за один вызов. Значения дат, IP,
пользователей, критерии выбора не брать из solution: использовать instruction и
collector note. На пилоте нужны свидетельства чтения всех shards и фактического
исполнения parser, затем точный official reward. Если вычисление не исполняется,
не добавлять ещё текста в forensic playbook.

## Как ограничить следующую серию

1. Сначала точный first-request replay N1 и public audit pilot; сохранить
   request/response timings и успешные действия. Если используется работающий
   стенд с новым состоянием, снять свежий B тем же архивом.
2. Проверить N2 либо N3 по результату пилота. До новой массовой серии добиться
   хотя бы одного содержательного public успеха. Не запускать все пять идей сразу.
3. Полная шестёрка: кандидат должен дать минимум 3/6, сохранить hello/bye и
   подтвердить новую победу ещё двумя повторами с чередуемым control. Ускорение,
   больше файлов и больше прочитанных строк — промежуточные измерения, не приёмка.
4. Только затем новые нейтральные мутации official-кейса и дополнительные 18;
   таблицы separate, сравнение per-task gained/lost. H05a оставить в отдельной
   очереди подтверждения, не объявлять ни принятым, ни опровергнутым.

Пока **ни одна новая гипотеза не доказана по solved**. Доказаны конкретная ошибка
фазового бюджета и отсутствие нужных действий в сохранённых public-траекториях.
Следующий успех нельзя обещать до эксперимента; теперь эксперимент способен
отделить исправление механизма от ещё одной косметической перестановки prompt.
