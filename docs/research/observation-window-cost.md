# Чего стоит сдвиг окна наблюдений — замер по E033 и E034

Дата: 04.09.2026. Данные — `build/eval-E033-repeat`, `build/eval-E034-prompt-order`.
Команда воспроизведения — в конце.

## Наблюдение

Длительность `plan`-вызова по номеру шага, медиана в секундах (шаги, где хотя бы три
задачи дошли):

| шаг | E033, медиана | E034, медиана |
|---|---|---|
| 1 | 39.2 | 48.7 |
| 2 | 6.5 | 7.4 |
| 3 | 10.6 | 9.1 |
| 4 | 7.6 | 9.1 |
| 5 | 8.6 | 8.2 |
| 6 | 7.6 | 7.4 |
| 7 | 7.0 | 9.1 |
| 8 | 7.8 | **15.2** |
| 9 | **22.5** | **23.6** |
| 10 | 26.1 | 31.7 |

Первый вызов дорог понятно: он платит prefill за весь системный блок. Дальше вызовы
стоят 7–9 с — сервер переиспользует префикс и платит почти только за decode. С девятого
шага цена утраивается, и **не разово**: десятый дороже девятого.

## Причина — в коде, а не в модели

`agent/prompt.py:158`:

```python
kept = observations[-limits.OBSERVATION_WINDOW :]
dropped = len(observations) - len(kept)
messages = [{"role": "system", "content": system}]
if dropped:
    messages.append({"role": "user", "content": f"[{dropped} more earlier observations omitted]"})
```

`OBSERVATION_WINDOW = 8` (`agent/limits.py:65`). Пока наблюдений восемь или меньше,
каждый следующий запрос — строгое расширение предыдущего: сервер держит префикс и
дописывает хвост. На девятом шаге происходит сразу два разрыва:

1. самое старое наблюдение выпадает из окна, то есть текст сразу после системного блока
   меняется;
2. появляется сообщение `[N more earlier observations omitted]`, и **N растёт на каждом
   следующем шаге** — то есть префикс расходится не один раз, а на каждом вызове до
   конца задачи.

Из-за второго пункта после шага 9 переиспользовать нечего вообще: с точки зрения
сервера каждый запрос начинается с нового текста на второй позиции.

## Сколько это стоит

В E033 на шаги ≥ 9 приходится 21 вызов и ≈ 481 с из 2446 с всего времени `plan` (20%).
Если бы они стоили как шаги 2–8 (≈ 8 с), суммарная экономия — около 330 с на 18 задач,
то есть ≈ 18 с на задачу при бюджете 180 с. Выигрыш достаётся ровно тем задачам, которые
дошли до девятого шага, то есть длинным — а это и есть класс timeout.

## Что с этим делать (не сделано)

Форма, которая устраняет обе причины, — **append-only до порога с однократной
перезакладкой**: история дописывается и никогда не переупорядочивается, пока оценка
контекста не подойдёт к `n_ctx`; тогда один раз собирается сжатая история, платится один
полный prefill, и дальше снова только дописывание. Счётчик пропущенных наблюдений при
этом либо исчезает, либо переезжает в конец, где он не рушит префикс.

Чистый append-only уже мерян: E021/E025 дали −23% на вызов ценой +40.6% токенов. Порог с
перезакладкой ограничивает как раз эту цену. Токены — третий критерий ранжирования,
solved — первый, поэтому размен допустим, но подтверждать его нужно прогоном, а не
рассуждением: `n_ctx = 4096`, и длинная задача может упереться в контекст раньше, чем
получит выигрыш.

## Воспроизведение

```sh
python3 - <<'PY'
import sys, statistics
sys.path.insert(0, '.')
from pathlib import Path
from scripts.eval.timing import read_run
for run in ('build/eval-E033-repeat', 'build/eval-E034-prompt-order'):
    by = {}
    for task in read_run(Path(run)):
        step = 0
        for _, phase, duration in task.steps:
            if phase == 'plan':
                step += 1
                by.setdefault(step, []).append(duration)
    print('==', run)
    for key in sorted(by):
        if len(by[key]) >= 3:
            print(f'{key:5d}{len(by[key]):4d}{statistics.median(by[key]):8.1f}')
PY
```
