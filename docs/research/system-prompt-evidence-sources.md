# Реестр первичных источников и проверок

## Li et al. (2024), Measuring and Controlling Instruction (In)Stability in Language Model Dialogs

- URL: https://arxiv.org/html/2402.10962v4
- Код и данные: https://github.com/likenneth/persona_drift
- Проверено 2026-08-25.
- Модель основной серии: LLaMA-2-Chat-70B, то есть **вне целевого диапазона 7B–32B**. В аннотации и тексте заявлено заметное instruction drift в течение восьми раундов диалога; это не является сравнением system-prompt форм для tool-using агента.
- Возможная релевантность: подтверждает, что закреплённая в начале инструкция ослабевает по ходу длинного диалога. Не даёт численного порога в токенах для 7B–32B и не сравнивает позицию задачи в системном промпте.
- Статус для итоговой таблицы: не использовать как прямое доказательство ни одного из девяти факторов; допустима только в разделе ограничений/контекста с явной маркировкой «70B, не tool-use».

## Berkeley Function-Calling Leaderboard, обзор 2024

- URL: https://gorilla.cs.berkeley.edu/blogs/8_berkeley_function_calling_leaderboard.html
- Код: https://github.com/ShishirPatil/gorilla/tree/main/berkeley-function-call-leaderboard
- Датасет: 2 000 пар вопрос–функция–ответ; выбор среди 2–4 функций в категории Multiple Function; метрики AST и executable evaluation.
- Статус: полезен как воспроизводимая метрика корректности вызова, но сам по себе не создаёт контролируемое сравнение prompt-форм. Не использовать для приписывания эффекта порядка, few-shot или native-vs-text без первичной таблицы/скрипта абляции.

## Предоставленные материалы

- `task.md` определяет закрытую бинарную оценку, ранжируемую также по input+output токенам. Это усиливает применимость только измерений, где prompt-токены и формат явно контролировались.
- `playbooks-draft.md` — черновик процедурных playbook'ов и notices, не содержит проверенных эмпирических абляций по форме системного промпта в просмотренном фрагменте.


## Saha et al. (EMNLP 2024), Sequential API Function Calling Using GraphQL Schema

Первичная страница: https://aclanthology.org/2024.emnlp-main.1083/; PDF: https://aclanthology.org/2024.emnlp-main.1083.pdf; software и data доступны на той же странице. Авторы заявляют открытые LLM-baselines на GraphQLRestBench с few-shot Chain-of-Thought и ReAct. Это перспективный первичный источник для фактора «явная ReAct-разметка против прямого вызова», но сравнение, размер моделей, exact-match/исполняемые метрики и численные дельты ещё не извлечены из PDF. До извлечения не делать содержательных выводов.


## Kim et al. (2024), LLMCompiler

Первичный HTML: https://arxiv.org/html/2312.04511; код: https://github.com/SqueezeAILab/LLMCompiler. В аннотации заявлено до 3.7× ускорения, 6.7× снижения стоимости и около 9% роста accuracy против ReAct, но это **архитектурное сравнение планировщика с параллельным исполнением**, а не чистая абляция текста system prompt, ReAct-разметки или native function calling. До проверки используемой базовой модели и конкретных таблиц не использовать в основной таблице как измерение вопроса пользователя. Кандидат для раздела «непереносимые результаты».


## Gui et al. (2024), Look Before You Leap / ToolDEER

Первичный HTML: https://arxiv.org/html/2402.16696; код: https://github.com/Ericmututu/ToolDEER. Статья использует 900 случайно отобранных инструментов для построения набора Decision-Call (8 650 samples; 3 460 NoCall и 5 190 Call). В доступной таблице приведены точности decision-task, а не контролируемый рост ошибки при 1→N одновременно показанных инструментов: ToolDEER-7B = 94.1±1.6 (Decision-Search) и 98.4±2.4 (Decision-Call), ToolDEER-13B = 95.9±1.9 и 99.2±0.4. Поэтому источник подтверждает масштаб исходного tool pool, но не доказывает порог числа инструментов в системном промпте; не использовать как ответ на фактор 6 без дополнительного первичного сравнения.


## Liu et al. (TACL 2024), Lost in the Middle

Первичная статья: https://aclanthology.org/2024.tacl-1.9/; репозиторий: https://github.com/nelson-liu/lost-in-the-middle. В аннотации зафиксирован качественный вывод: при multi-document QA и key–value retrieval на длинном контексте показатели часто максимальны, когда релевантная информация находится в начале или в конце, и существенно падают в середине. Это соответствует вопросу о позиции задачи лишь по механизму позиционного смещения, но **не является system-prompt/tool-agent измерением**. Нельзя переносить на порядок блоков или положение задачи без оговорки. Требуется извлечь опубликованные численные точки из графиков/репозиторных результатов, иначе итоговый отчёт будет перечислять его только как качественный контекст, а не как ответ таблицы.


## Harada et al., Curse of Instructions / ManyIFEval

Первичная запись: https://openreview.net/forum?id=R6q67CDBCH. Доступ к PDF в этом сеансе закрыт browser verification. По метаданным исследование использует ManyIFEval с 1–10 проверяемыми инструкциями и сообщает, что вероятность выполнить все инструкции резко падает с их количеством; также сравниваются Llama 3.1 и Gemma 2. Однако численные результаты, доступные в поисковой выдаче, приведены только для крупных закрытых моделей (GPT-4o: 15%→31% с self-refinement на 10 инструкциях; Claude 3.5: 44%→58%). Не переносить эти числа на 7B–32B и не помещать в основную таблицу как ответ на фактор «длинные условные конструкции/противоречия» до извлечения таблиц Llama/Gemma из первичного PDF или кода.


## Hao et al. (NeurIPS 2023), ToolkenGPT

Первичный HTML: https://arxiv.org/html/2305.11554; код: https://github.com/Ber666/ToolkenGPT. Базовая модель всех методов — LLaMA-13B (проверяется в тексте experiments; сам метод дополнительно обучает эмбеддинги инструментов). В Table 2 на GSM8K-XL (4 инструмента) и FuncQA (13 инструментов) приведены: CoT 0.18/0.20/0.03; ReAct 0.32/0.57/0.06; ToolkenGPT 0.33/0.73/0.15 соответственно для GSM8K-XL, FuncQA one-hop и FuncQA multi-hop. Следовательно, на FuncQA ToolkenGPT превышает ReAct на +0.16 (one-hop) и +0.09 (multi-hop); но это результат **обучения новых tool-token embeddings**, а не смены системного промпта при фиксированной локальной модели. Его нельзя выдавать за эффект native API tool calling и нельзя использовать как основное измерение фактора 1. ReAct-vs-CoT при LLaMA-13B не является честной абляцией одной разметки без проверки деталей prompts и числа вызовов; не использовать без этой оговорки.


## Mu et al. (2025), A Closer Look at System Prompt Robustness

Первичный HTML: https://arxiv.org/html/2502.12197; код и данные: https://github.com/normster/RealGuardrails. Работа непосредственно измеряет устойчивость к конфликтующим system/user-инструкциям и содержит AgentDojo prompt, но в текущей доступной странице поиск точного идентификатора Llama-3.1-8B не дал результата. Её нельзя использовать как численное доказательство порядка блоков, позиции задачи, положительных/отрицательных правил или проверки перед завершением без извлечения конкретных таблиц и модели. Оставить как проверенный источник о том, что этот класс проблем измеряется, но не как доказательство нужной дельты.


## EASYTOOL: проверка репозитория

В репозитории https://github.com/microsoft/JARVIS/tree/main/easytool имеются данные/инструкции для FuncQA, RestBench и ToolBench, а README запускает доступные эксперименты с GPT-3.5, не с Vicuna. Таким образом, код и преобразованные tool instructions воспроизводимы, но README не содержит численных таблиц статьи. Первичная опубликованная статья подтверждает тезис «concise unified instruction снижает token consumption и повышает tool utilization», однако точный процент/число токенов пока не извлечён. Нельзя подменять этот пробел числом из abstract и нельзя утверждать конкретный порог длины описания.


## EASYTOOL: уточнение по первичному HTML

HTML-копия доступна по https://arxiv.org/html/2401.06201. Подтверждено, что сравнение Vicuna-13B-based RestGPT идёт с ToolDec; авторы также заявляют уменьшение incorrect tool usage. Однако встроенное извлечение не вывело содержимое нужных таблиц. Следующий этап — локально извлечь из сохранённого HTML именно Table 3–5 и определить, сравнивают ли они фиксированную базовую модель и только документацию; только такое сравнение годится для фактора 6.


## Meta Llama 3.1 evaluation details

Официальный протокол: https://github.com/meta-llama/llama-models/blob/main/models/llama3_1/eval_details.md. Он документирует Llama 3.1 8B/70B/405B и разные 0-/5-shot режимы для общих benchmark, но **не даёт парного 0-vs-few-shot сравнения на function calling**: BFCL запускается по исходному 0-shot prompt; API-Bank также 0-shot custom prompt; Gorilla API Bench использует исходный 0-shot protocol. Следовательно, даже официальные результаты 8B не отвечают на фактор 3; не использовать MMLU как замену tool-use evidence.
