# Разбор M13: что шесть публичных верификаторов считают за `reward=1`

Дата: 25.08.2026. Источник — `verifier-contract.md` (запрос M13 из
`docs/prompts/manus-prompts.md`), sha256 выгрузки
`1783a1632d4c69c833d98d6698e700809f47f292f72026922a45e76e6501c5b5`.

Отчёт закрывает находку враждебного разбора «финальный output-контракт неизвестен, а
verifier проверяет лишь гипотезу агента». Закрывает её **для шести публичных задач** —
и сам отчёт настаивает на этой границе сильнее, чем настаивали бы мы.

## 1. Достоверность

Перепроверено с нашей машины загрузкой первоисточников на указанном коммите
`71f9081`, независимо от исполнителя отчёта.

| Утверждение отчёта | Проверка | Результат |
|---|---|---|
| `bye-file`: проверяется `-f /app/bye.txt` и равенство строке `Bye` | загружен `local_task/bye-file/tests/test.sh` | совпало; дополнительно виден путь награды `/logs/verifier/reward.txt`, которого в таблице отчёта нет — он его намеренно не разбирал |
| `incident-log-forensics`: ровно 4 непустые строки, `^[a-z_]+=.+$`, отказ при подстроке `" = "`, `sort` обоих файлов перед `diff -q` | загружен `local_task/incident-log-forensics/tests/test.sh` | совпало дословно, включая нетипичную проверку `" = "` |
| Ни один verifier не читает stdout агента | сверено по двум загруженным скриптам | в обоих подтверждено; остальные четыре приняты на слово |

Три источника из тридцати проверены загрузкой. Остальные — в том числе pytest-тесты
`find-sqli-login` и обе SQLi-fix задачи — приняты на слово. Это осознанный размер
выборки, а не полная верификация: две проверенные точки были выбраны как наиболее
«хрупкие» (точное сравнение строки и цепочка из четырёх условий подряд), и обе
сошлись дословно.

## 2. Что действительно доказано

**Главный результат — отрицательный, и он самый ценный.** Ни один из шести
верификаторов не читает stdout агента. Награда во всех шести определяется состоянием
среды: файл по абсолютному пути либо HTTP-поведение сервиса, поднятого из `/app`.

Отсюда следует правило финализации, которое можно принимать без оговорок, потому что
оно верно в обе стороны:

> Идеальный текст в stdout не компенсирует отсутствующий артефакт. Диагностика в
> stdout при верном артефакте ничему не вредит.

Второе доказанное: **абсолютный путь важнее семантической правильности**. Верный
патч в `/tmp/routers/auth.py` — ноль, потому что verifier запускает `main:app` из
`/app`. Верный `Hello` в `/tmp/hello.txt` — ноль по той же причине.

Третье: семантик сравнения внутри одной публичной шестёрки уже **четыре** — shell
equality после `cat`, JSON-разбор с подстрочными сигналами, HTTP-ассерты, построчный
gating плюс sorted diff. Единого «формата ответа» не существует даже здесь.

## 3. Чего отчёт не доказывает

Отчёт сам отвёл под это раздел 6, и мы принимаем его формулировки целиком. Ни одно из
свойств шести задач не переносится на закрытые 15: ни `/app` как место артефакта, ни
игнорирование stdout, ни `tests/test.sh`, ни `allow_internet=true`, ни таймауты.

Практический вывод для агента поэтому формулируется **как требование к способности, а
не как знание о формате**: агент обязан уметь материализовать проверяемое изменение в
среде и не имеет права считать stdout доставкой результата. Это robust design, а не
контракт закрытого набора.

## 4. Что меняется у нас

| Что | Куда | Статус |
|---|---|---|
| Правило «stdout не является deliverable» | политика финализации будущей петли | принято, реализуется вместе с петлёй |
| Восемь негативных фикстур из §5 | задача «Negative contract fixtures» в `HANDOFF.md` | принято как готовая спецификация: каждая строка уже содержит вход, ожидаемый `0` и ветвь verifier |
| Наблюдение «диагностика в stdout безопасна» | ограничение на объём логов | принято: логировать можно, но лог не заменяет артефакт |
| Значения таймаутов (120/600 с агент, 120/240 с verifier) | `agent/limits.py` | **не переносится**: это значения шести публичных `task.toml`, а `Budget` уже читает лимит из среды и не должен получать зашитую константу |

Кода этот разбор не меняет. Восемь фикстур нельзя написать раньше, чем появится сам
слой финализации: проверять сейчас нечего, а тест без предмета — это тест на заглушку.

## 5. Что дальше

1. Когда появится финализация — реализовать восемь фикстур §5 один в один, включая
   случай 7 (пробел перед `=`) и случай 4 (диагностическая строка ломает JSON).
2. Не выводить из отчёта общий «формат финального ответа»: его нет. Выводится только
   способность класть результат туда, куда указывает инструкция задачи.
3. При импорте upstream snapshot (S0.1) сверить таблицу §2 с фактическими файлами:
   тогда проверка станет полной и дешёвой, без сети.
