## Две проблемы достоверности измерений

**Повторное имя перезаписало контроль предыдущей ночи.** Обе очереди использовали
`build/eval-B1-base-public`. В `deep-queue-summary.tsv` старый B1 — 87 826 tokens;
текущий TSV в этом каталоге — 98 992. Реальный запуск
`python3 docs/research/night-public-replay.py` теперь падает на проверке суммы
токенов. Проверены все 20 старых строк: это единственное расхождение суммы.
Старый агрегат и анализ сохранены в Git в A20260907c, но прежние сырые B1 нельзя
считать неизменными. Новые результаты должны иметь уникальный идентификатор
даты/архива/повтора и никогда не перезаписывать завершённый каталог.

**Локальный reward не гарантирует завершение в лимит.** В новом B1 `bye-file`
имеет reward=1, но agent_exit=124, stop=killed, wall=120,1 с. `run_suite.py`
вызывает verifier и после kill; классификатор ставит успеху failure="-". Поэтому
2/6 — результат локального checker, а только 1/6 одновременно имеет reward=1
и завершение без kill. По изложенным условиям соревнования timeout — ноль;
это расхождение необходимо проверить настоящим Harbor-контрактом. Нельзя
молча заменить опубликованное 2/6 на 1/6: нужны обе отдельные метрики.

Колонка `wrote` также определяется по ответам модели в trace, а не снимку файлов.
Она не доказывает ни исполнение записи, ни исправление приложения.

### Времени стало больше, полезных действий — недостаточно

На одинаковых трёх задачах база имеет четыре `ep_late`, N2 — ноль. Это согласуется
с ожидаемым действием снятого ограничения timeout, но без повторов и последующего
контроля не доказывает устойчивость или причину всех изменений latency.

Audit N2 четыре раза запрашивает список корня, затем трижды ищет конкретный импорт
SQLAlchemy, после чего четыре раза записывает пустой findings. Отсутствие одного
импорта не проверяет отсутствие SQLi. Ни одного `read_range` или shell в этой trace.

Fix-login N2 тратит 480,5 с и 48 376 tokens против 232,7 с и 17 701 у B1:
примерно 2,1× времени и 2,7× токенов при том же нуле. Единственное чтение —
AGENTS.md с 10-й строки; его успешное исполнение видно в request body. После
советов о stale server модель запрашивает проверку процессов и повторные pkill,
хотя до этого не предъявила ни изменения кода, ни воспроизводимого сбоя.
Далее — **18 запросов записи README**, один finish с `cat README`, без чтения
обработчика и без запроса запуска pytest. В сохранённом README заявлено, что
уязвимость исправлена и тесты прошли. Ни trace, ни список файлов этого не подтверждают.

Сам N2 оставляет прежнюю раннюю подсказку записи. Он снимает ограничение вызова,
но не исправляет цель действий. Увеличение MAX_STEPS или общего бюджета не выглядит
первоочередной ставкой по этой траектории.

### Кандидат подменён заметкой, входные данные — предположениями

В B1 audit второй вызов действительно даёт TimeoutError, после чего в запросе
появляется «Запиши лучший вариант через write_file сейчас». В loop любая запись
попадает в `state.artifacts` и разрешает остановку по stuck. Для ремонта приложения
README не является кандидатом решения; для аудита пустой список без исследования
не является доказательством отсутствия дефекта.

На обоих fix в B1 исходный `pytest tests/` дал **15 passed** ещё до правки.
Это контроль обычной функциональности, а не проверка устранения SQLi. Для зачёта
нужны отдельные проверка безопасности и регрессия. Точная причина каждого FAIL
официального fix-checker не сохранена в обычных логах; общий label reasoning не
заменяет журнал его assertions.

Forensics B1 успешно получает listing `/app/incident`, затем читает
`/app/collector_note.txt` и получает FileNotFoundError. Правильный путь указан
в исходном брифинге, но результат list_dir содержит только имена без родителя,
а история сообщений не сохраняет аргументы действий. Поздний запрос правильного
пути имеет `start_line=0`, против контракта 1-based. Дальше семь запросов записи
отчёта с unknown/0. Чтения самих журналов и запуска parser нет.

Основной JSONL — 5 792 840 байт; восстановленный фрагмент — 808 байт, edge shards —
528 и 205. Даже исправление пути не заменит выборку и корреляцию всех источников:
пытаться переслать весь JSONL в малое окно контекста нецелесообразно.
`check_parity.py` организаторов заново завершился с exit 0.

## Что проверять следующим

1. **Сначала диагностический public audit с предоставленным исходником.** Та же
   модель, исходная инструкция и релевантный файл из environment, без solution,
   эталонного отчёта и тестов checker в контексте. Внешняя оценка — официальный
   checker плюс проверка, что evidence соответствует исходнику. Если даже так
   отчёт неверен, навигация не объясняет всё. Это assisted diagnostic, не public
   score. В прежнем плане такой опыт был, результатов его treatment здесь нет.
2. **Если диагностика успешна — автономная доставка кода до первого кандидата.**
   Начать с уже собранного N3 на одном public audit. Проверить исполненное чтение
   обработчика, а не упоминание пути в prompt. N3 выдаёт индекс импортов и имён
   функций, а не их тела: если список снова игнорируется, следующий отдельный
   вариант — ограниченные фрагменты достижимых функций с путями и строками.
   Выбор по импортам и потоку данных, без имён задач и известных ответов.
3. **Следом — контракт результата для code-fix.** Результат — изменения исходников
   и поведения, а не произвольный новый файл. Малый diff, воспроизводитель дефекта
   до/после, обычные tests. Ранний checkpoint должен сохранять работу нужного
   вида, не требовать от всех задач написать отчёт. Проверять сначала fix-login,
   затем fix-search; не объединять этот фактор с N3 без сравнения отдельных сторон.
4. **Для forensics — вычисления по файлам, а не генерация полей из памяти.** Сначала
   однозначные пути и успешное чтение collector note, затем исполняемый parser:
   восстановленные audit-записи, связь по request id с proxy/XFF и всеми edge
   shards, точные поля по условию. Модель формулирует выборку, локальная программа
   считает и выдаёт компактные свидетельства. Формат проверяется отдельно от
   содержимого. Не переносить критерии/значения из reference solution в агент.
5. **Поддержка инструментов и наблюдений — только по месту сбоя.** Полный путь в
   listing, запрошенные аргументы рядом с результатом, понятные ошибки диапазона;
   выявление повторов чтения/README без изменения состояния задачи. H01a/H01b/H08
   уже не дали public-прироста, поэтому повторять их массовую очередь без нового
   механизма нельзя. Это вспомогательные проверки после полезного входа, не
   самостоятельное обещание баллов.

Альтернатива для контрольного опыта после assisted diagnostic — минимальный
single-loop, где доступен исходник и нет принуждения к произвольному файлу.
Сравнивать по public reward с текущим контроллером. Если простой вариант проходит,
сложность существующей петли должна оправдать себя данными. Переписывать всё
решение до этого сравнения оснований нет.

## Как расходовать следующие прогоны

Первый целевой рубеж — **устойчивые 3/6 public**, включая один содержательный
успех и сохранение обеих простых задач. Это критерий эксперимента, не прогноз.

Порядок: один audit-пилот → повтор новой победы → полная шестёрка → ещё два
подтверждения содержательной победы с чередуемым control → оба fix → forensic.
Точное имя public задачи допустимо в eval-команде, не в runtime. После public
прироста — нейтральные переименования/переносы и safe-code контроль, затем 18 extra
как регрессия. Таблицы public и extra всегда раздельные.

Для каждой траектории сохранять первый успешный read, первый содержательный
кандидат, diff/отчёт, команду и результат проверки, причину стопа, фактические
input/output tokens. `solved_claim`, wrote и число шагов — вторичные сигналы.
Нужны весь журнал действий с аргументами и ответами, официальный verifier stdout
и состояние CPU/GPU/контекста. Снимок перед ночью в `build/n3-evidence/metadata.json`
показывает **100% CPU**, а карточка N1 описывает partial GPU offload: состояние
всей ночи по одному снимку установить нельзя.

У прошлой полной очереди 76% суммарного task wall ушло на дополнительные fixtures,
а четыре содержательные public не решились ни в одном из десяти вариантов.
Возвращаться к очереди «восемь вариантов × оба набора» до первого нового public
успеха не предлагается. N1 ускорил старт, но оставил четыре audit-нуля; N2 не
прошёл полный gate; N3 ещё не измерен. Экономия токенов, macro, другая модель и
увеличение контекста сейчас уступают проверке доставки данных и исполнения ремонта.
