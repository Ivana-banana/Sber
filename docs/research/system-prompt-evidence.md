# Форма системного промпта для tool-using агента 7B–32B

**Дата проверки:** 25 августа 2026 года. **Назначение:** локальный автономный агент с OpenAI-совместимым endpoint, неизвестными моделью и сервером, разнородными задачами и бинарной оценкой. **Вердикт:** из девяти запрошенных факторов нашлось одно пригодное для вашей размерной зоны измерение — не «магия порядка» или ReAct, а замена длинных описаний инструментов компактными структурированными инструкциями. По остальным восьми факторам я не нашёл контролируемой, численно опубликованной абляции, которая одновременно держит фиксированными модель и агентную обвязку, меняет ровно нужную форму промпта и измеряет tool-use на модели 7B–32B. Ниже «нет измерения» означает именно это, а не утверждение, что эффект отсутствует.

> **Критерий включения.** В основную рекомендацию попадает только сравнение, где известны модель, benchmark, метрика, числа и ссылка; при этом меняется только текст/формат промпта либо явно описанная часть tool-инструкции. Если меняются веса, архитектура, число шотов, доступные tool descriptions или планировщик, результат остаётся полезным контекстом, но не становится причинным эффектом запрошенного фактора.

**Как читать строку 6.** Это не доказательство, что «748 токенов — универсальный порог» и не доказательство преимущества одной лишь краткости. Однако это наиболее близкое к вашей постановке воспроизводимое наблюдение: замена длинной разнородной документации на компактный единый tool-contract у 7B-моделей совпала с переходом от нулевого среднего Success к 37,3–47,0. В вашем конкурсе это особенно релевантно, потому что input tokens участвуют в ранжировании; но перенос должен быть проверен на вашем endpoint.

**Почему строки 1–2 не являются доказательством.** Результаты ToolkenGPT иногда ошибочно цитируют как победу «нативного вызова» над текстом, а таблицу GraphQLRestBench — как победу ReAct. В первой работе учатся новые embeddings инструментов; во второй неравны число демонстраций и объём descriptions. Обе причины ломают требуемую причинную интерпретацию. [3] [4]

## 2. Ломающие формулировки

Этот раздел — **не перечень измеренных эффектов**. Это компактные тестовые анти-примеры, которые стоит включить в локальную регрессию, потому что они создают несовместимые требования или конфликт форматов.

| Класс | Формулировка, которую не следует помещать в один контракт | Почему это конструктивно плохо | Безопасная переработка |
|---|---|---|---|
| Противоречие о действиях | `Всегда вызови инструмент перед ответом. Верни ответ без вызова инструмента.` | Для одних и тех же входов заданы несовместимые действия, а при неизвестной модели нет гарантированного правила приоритета между строками. | Сформулировать один контракт: `Вызывай инструмент, когда наблюдаемый факт нужен для выполнения задачи; иначе возвращай ответ.` |
| Противоречие о завершении | `Не завершай задачу, пока не проверил результат. Заверши немедленно после изменения файла.` | Одна строка требует verifier step, другая запрещает его фактической остановкой цикла. | `После изменения файла выполни локальную проверку; после PASS сообщи итог.` |
| Длинная вложенная условная конструкция | `Если A, кроме случая B, но только когда C уже проверен, если не D, иначе…` | Модель должна удержать множество ветвей и исключений; ошибка в scope одного исключения меняет действие. | Разложить на независимые короткие правила с явным порядком: условия входа → действие → критерий перехода. |
| Reasoning + строгий JSON | `Рассуждай подробно шаг за шагом и верни только валидный JSON.` | Развёрнутый текст и «только JSON» — разные каналы вывода; текст рассуждения делает JSON невалидным при строгом парсере. | Развести интерфейсы: API tool call/JSON содержит только schema; человеку возвращается краткий результат после выполнения. |
| Неопределённый scope | `Проверь всё и исправь все проблемы.` | Не определены границы файлов, критерий готовности и бюджет; агент может тратить лимит на бесконечный обход. | `Проверь артефакты, затронутые задачей; для каждого изменения сохрани проверку; остановись при исчерпании бюджета.` |

Работа ManyIFEval измеряет ухудшение выполнения всех инструкций по мере увеличения их числа, но доступные в ходе проверки числа `15%→31%` и `44%→58%` относятся к GPT-4o и Claude 3.5 при self-refinement, а не к целевым 7B–32B. Поэтому она объясняет, почему эти анти-примеры нужно тестировать, но не доказывает их величину для вашего агента. [7]

## 3. Скелет системного промпта

Ниже **604 Unicode-символа и 73 слова** вместе с `{TASK}`. При неизвестном tokenizer нельзя честно сертифицировать один универсальный токенный счётчик; этот объём оставляет большой запас относительно лимита 700 токенов для обычных современных subword tokenizers. Перед submission следует посчитать его tokenizer’ом endpoint и оставить резерв под tool schemas. Блок `{TASK}` должен содержать только конкретное задание запуска, а не повторять инструкции.

```text
РОЛЬ
Ты — автономный локальный исполнитель. Цель — проверяемое решение задачи.

ИНСТРУМЕНТЫ
Используй только предоставленные инструменты с точными именами и параметрами. Перед вызовом выбирай один минимальный следующий шаг.

РАБОТА
Сначала изучай файлы, сервисы и ограничения. Делай короткие обратимые шаги. При отсутствии сигнала переходи к следующей ветке. Береги бюджет.

ПРОВЕРКА
Для изменённого артефакта запускай локальную проверку. Объявляй успех после проверки, результат которой подтверждает требование.

ОТВЕТ
Возвращай: итог; изменения; команду проверки; наблюдаемый результат.

ЗАДАЧА
{TASK}
```

| Порядок блока | Обоснование | Статус обоснования |
|---|---|---|
| **Роль** | Одна короткая цель задаёт scope и не дублирует частные правила. | **Рекомендация**, прямой абляции порядка не найдено (строка 4). |
| **Инструменты** | Держит контракт инструментов компактным и точным; измеренная работа показывает, что длинные разнородные docs не следует целиком переносить в prompt. | **Частично измерено**: строка 6, [1] [2]. |
| **Правила работы** | Локализует бюджет и stop condition, нужные по контракту оценки; не добавляет few-shot траектории, для которых нет tool-use дельты. | **Рекомендация**: строка 3 не измерена; токенный риск задан вашей постановкой. |
| **Проверка** | Резервирует действие перед финалом и делает проверяемый результат явной частью цикла. | **Рекомендация**, не измеренный prompt-effect (строка 8). |
| **Ответ** | Краткий наблюдаемый журнал полезен для внешнего evaluator и не смешивает свободное рассуждение со строгими машинными форматами. | **Рекомендация**, не измеренный prompt-effect. |
| **Задача последней** | Это осознанно **не** объявляется доказанно лучшей позицией: такой ablation нет. Она оставлена последней ради разделения постоянного контракта и per-run входа. | **Рекомендация**, строка 4. |

Этот skeleton специально **не содержит** hidden chain-of-thought, few-shot примеров, names закрытых задач, длинных описаний инструментов и утверждения, что native calling «всегда лучше». При наличии native tool API сами схемы должны передаваться по API; при текстовом fallback формат должен быть одним коротким детерминированно парсимым action-contract. Выбор между ними — предмет локального измерения, а не вывод из приведённой литературы.

## 4. Фольклор: рекомендации без пригодного измерения

Следующие утверждения широко повторяются в agent/prompt практиках, но **не получают статус результата** для вашей постановки: «native function calling всегда лучше текстового ReAct», «ReAct всегда повышает успех малых моделей», «несколько few-shot примеров перестают быть полезны после 13B/32B», «задача обязательно должна быть первой/последней», «после N токенов system prompt малые модели неизбежно ломаются», «нужно показывать не более K инструментов», «положительные правила всегда лучше запретительных», «одна фраза про проверку заметно снижает false completion», «английский всегда лучше русского для tool calls».

К фольклору относится и более тонкий тезис: «требование думать и выдавать JSON ломает малые модели». Конфликт форматов реален как инженерный риск, но найденные материалы не дают воспроизводимой численной дельты именно на 7B–32B tool-agent. Его следует решать разделением machine-interface и человекочитаемого ответа, а не приписывать улучшение конкретному проценту.

Для неизвестного endpoint наиболее экономный путь — не выбирать между этими тезисами верой, а провести малую блокированную ablation: одинаковые задачи, seed/temperature/максимум шагов/timeout и toolset; менять **один** фактор; измерять binary pass, input+output tokens, invalid-call rate и false-completion rate. Сначала разумно проверить две ветви из строки 6: исходные tool docs против компактного tool-contract. Затем сравнить native endpoint с одним текстовым contract, а zero-shot с одним демонстрационным примером. Это даст данные именно для сервера оценки, не заменяя их данными чужих моделей.
