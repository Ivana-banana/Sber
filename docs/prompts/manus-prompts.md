# Промпты для Manus — работа над хакатоном AIRI

Каталог задач, которые имеет смысл отдавать Manus, а не решать внутри репозитория.
Каждый пункт: зачем он нужен, какие файлы прикрепить к сообщению, готовый текст
промпта и условия приёмки результата.

Правило отбора: в Manus уходит то, для чего нужен **интернет, чужие исходники или
долгий перебор источников**. Всё, что требует нашего кода, целевого образа или
измерения на реальном endpoint, остаётся в репозитории — Manus этого не видит и
проверить не может.

## Как пользоваться

1. Открыть новую сессию Manus на каждый промпт. Не смешивать две темы в одной
   сессии: отчёты становятся размытыми, а источники перепутанными.
2. Прикрепить ровно те файлы, что указаны в разделе «Прикрепить». Лишние документы
   уводят ответ в наши гипотезы вместо внешних фактов.
3. Скопировать текст промпта целиком, включая блок правил достоверности.
4. Готовый отчёт сохранить в `docs/research/` под указанным именем **как есть**,
   без правок, отдельным коммитом.
5. Написать короткий разбор в том же каталоге по образцу `docs/research/verdict.md`:
   что принято, что отклонено, что меняется в `PLAN.md` / `docs/decisions.md`.

## Гигиена

- **Не загружать** в Manus: `Тз сбер.docx` (первоисточник с условиями организаторов),
  `.env`, ключи, значения `OPENAI_API_KEY` / `OPENAI_BASE_URL`, сырые логи прогонов.
  Вместо ТЗ прикладывается нормализованный `docs/task.md`.
- Отчёт Manus — **недоверенные данные**, а не решение. Числа, лицензии и даты
  перепроверяются перед использованием (см. §1 `docs/research/verdict.md`: там
  проверка подтвердила отчёт, но это не отменяет процедуру).
- Ни один ответ Manus не попадает в `agent/` копипастой. В код идёт только то, что
  прошло наш разбор и записано решением.

## M1. Инвентаризация целевого образа `secureintelligent/acp`

**Зачем.** Мы не знаем, какие интерпретаторы, пакеты и CLI реально лежат в образе.
Из этого следует всё: какие инструменты может звать агент, нужен ли свой парсер,
поместится ли решение без зависимостей. На нашей машине Docker не поднимается
(блокер в `HANDOFF.md` от 2026-08-24), а у Manus есть песочница с интернетом.

**Закрывает.** Шлюз B `PLAN.md`, задачу «Инвентаризация target image» из `HANDOFF.md`,
открытый вопрос про digest в `docs/task.md`.

**Прикрепить.**

| Файл | Зачем |
|---|---|
| `docs/task.md` | имя образа, ограничения среды, что считается нулём |
| `HANDOFF.md` | формулировка блокера, чтобы Manus не предлагал «просто запустите docker» |

**Промпт.**

```text

secureintelligent/acp и отдать его в машиночитаемом виде.

Контекст. Мы сдаём автономного агента, который выполняется внутри этого образа в
изолированной microVM без интернета и без возможности установить зависимости. Всё,
чего в образе нет, для нас не существует. На нашей машине Docker недоступен, у тебя
песочница с интернетом есть.

Что сделать.

1. Найти образ в публичных реестрах (Docker Hub, ghcr, любой другой). Перечислить
   все доступные теги с датами и digest'ами. Если образа нет в публичном доступе —
   сказать это прямо и остановиться, не подменяя его похожим.
2. Получить содержимое. Если docker в песочнице доступен — pull и inspect. Если нет
   — работать через registry HTTP API (манифест + скачивание слоёв) либо skopeo/crane
   и распаковывать слои как tar. Указать, каким способом реально получен результат.
3. Снять и выписать:
   - digest и дату сборки каждого проверенного тега, ENTRYPOINT, CMD, WORKDIR, USER,
     переменные окружения из конфигурации образа;
   - версию ОС и базовый дистрибутив;
   - все версии python в образе, полный `pip freeze`/`pip list` для каждой;
   - наличие и версии: git, curl, wget, rg/ripgrep, grep, jq, sqlite3, unzip/zip,
     tar, patch, gcc/make, gdb, objdump/readelf/strings/file, nmap, netcat, tcpdump,
     tshark, openssl, node, java, php, docker/podman;
   - наличие и версии agent-фреймворков и SDK (harbor, openai, anthropic, litellm,
     langchain, requests, httpx, pydantic и всё похожее);
   - размер образа и распакованной файловой системы.
4. Отдельно проверить и явно ответить на три вопроса:
   - какая версия Harbor установлена и где лежат её исходники внутри образа;
   - есть ли в образе предустановленный пример агента или шаблон запуска;
   - какие инструменты форензики и реверса присутствуют, а какие отсутствуют.

Формат ответа.

1. Таблица «инструмент | есть/нет | версия | путь» — только проверенное.
2. Полный `pip list` каждой найденной python-среды, дословно, в блоке кода.
3. JSON-манифест: {image, tag, digest, os, python: [...], pip: {...}, tools: {...}}.
4. Точные команды, которыми ты это получил, чтобы мы повторили у себя.
5. Раздел «чего в образе нет» — по списку из пункта 3, отдельным перечнем.

Правила достоверности. Каждая строка — результат выполненной команды, а не
предположение по README или по типовому образу. Не смог проверить — пиши
«не проверено» и объясняй почему. Не заменяй образ похожим и не достраивай список
пакетов по логике «обычно там есть».
```

**Приёмка.** Есть digest, есть дословный `pip list`, есть команда воспроизведения.
Ответ без digest или со списком пакетов «по памяти» — брак, переспрашиваем.

## M3. Поведение малых моделей за OpenAI-совместимым endpoint

**Зачем.** В `agent/llm.py` уже реализована липкая деградация
`native tool calls → JSON schema → JSON object → text`, но стартовый уровень
`DEFAULT_CALL_STYLE` — догадка до прогона `scripts/probe_endpoint.py`. Manus может
собрать внешние данные о том, что реально ломается у малых моделей на vLLM,
llama.cpp, Ollama, SGLang и TGI.

**Закрывает.** Риск «локальная модель плохо вызывает tools» из `PLAN.md`, решения по
протоколу от 2026-08-25 в `docs/decisions.md`.

**Прикрепить.**

| Файл | Зачем |
|---|---|
| `agent/llm.py` | что уже реализовано, чтобы Manus не пересказывал наш же код |
| `agent/ports.py` | контракты вызова и типы ошибок |
| `scripts/probe_endpoint.py` | как мы собираемся измерять уровень протокола |
| `docs/decisions.md` | принятые решения: probe отменён, повтор на том же уровне запрещён |

**Промпт.**

```text
Задача: собрать внешние факты о том, как малые локальные модели (примерно 7B–32B) за
OpenAI-совместимым endpoint ведут себя при вызове инструментов, и проверить нашу
реализацию клиента на несовпадение с реальностью.

Контекст. Наш агент ходит в единственную локальную модель по OPENAI_BASE_URL с
OpenAI-совместимым API. Имя модели приходит в LOCAL_AGENT_MODEL, заранее неизвестно.
Интернета в проде нет, зависимостей ставить нельзя, клиент написан на stdlib. В
приложенном llm.py реализована липкая лестница деградации: native tool calls →
JSON schema (response_format json_schema) → JSON object → свободный текст с
парсингом. Понижение уровня разрешено, повтор на том же уровне запрещён, потому что
при temperature=0 ответ будет байт-идентичным.

Что выяснить, по внешним источникам (документация серверов инференса, issue-трекеры,
release notes, отчёты о воспроизводимых сбоях).

1. Какие серверы инференса реально отдают OpenAI-совместимый /v1/chat/completions и
   чем их поведение отличается: vLLM, SGLang, llama.cpp server, Ollama, TGI, LM Studio.
2. Для каждого: поддерживается ли tools/tool_choice, поддерживается ли
   response_format json_schema и json_object, что происходит при неподдерживаемом
   параметре — ошибка 400, тихое игнорирование или падение.
3. Какие типовые дефекты выдачи малых моделей задокументированы: обрамление JSON в
   тройные кавычки, преамбула перед JSON, одинарные кавычки, trailing comma, обрезка
   по max_tokens, повтор одного и того же tool call, вымышленные имена инструментов,
   вызов с пустыми аргументами, tool_calls вперемешку с текстом.
4. Отдаёт ли каждый сервер поле usage и при каких условиях его нет (стриминг,
   ошибка, кэш). Это критично: у нас токены — второй критерий ранжирования, и
   незамеренные токены мы помечаем, а не оцениваем.
5. Какие HTTP-коды и тела ошибок означают «этот параметр не поддерживается» против
   «endpoint перегружен» — то есть где деградировать, а где ждать.
6. Что известно про поведение при отсутствующем или пустом api key на локальных
   серверах.

Отдельно: прочитай приложенные llm.py, ports.py, probe_endpoint.py и назови места,
где наша реализация разойдётся с реальным поведением хотя бы одного из серверов
пункта 1. Не переписывай код, не предлагай рефакторинг стиля — только конкретные
расхождения и чем они грозят.

Формат ответа.

1. Матрица «сервер | tools | json_schema | json_object | usage | известные подвохи»
   со ссылкой на источник в каждой ячейке, где он есть.
2. Список дефектов выдачи с частотой упоминания и минимальным примером кривого
   ответа для каждого — нам нужны фикстуры для парсера.
3. Рекомендация по стартовому уровню лестницы с обоснованием: какой уровень
   безопаснее как значение по умолчанию, если сервер неизвестен.
4. Таблица «наш код | реальность | последствие» по расхождениям.

Правила достоверности. Ссылка на документацию или issue обязательна для каждого
утверждения о поведении сервера. Не смешивай API облачного OpenAI с локальными
реализациями. Неизвестно — пиши «не проверено».
```

**Приёмка.** Есть матрица со ссылками и минимум пять минимальных примеров кривого
вывода, пригодных как фикстуры для теста парсера.

## M4. Дистилляция четырёх доменных playbook'ов

**Зачем.** Решением от 2026-08-25 в prompt входит ровно один playbook, выбранный по
классификации задачи, бюджет — не более 400 токенов на активный playbook. Источники
уже найдены в M0 (Ghost scan-code, SWE-agent default.yaml, Linux Log Forensics,
ctf-skills), но текст ещё не выжат и лицензионные notices не собраны.

**Закрывает.** Шлюз C `PLAN.md`, задачу `THIRD_PARTY_NOTICES.md` из `HANDOFF.md`.

**Прикрепить.**

| Файл | Зачем |
|---|---|
| `docs/research/manus-skills-report.md` | список источников с лицензиями, уже отобранный |
| `docs/research/verdict.md` | что мы приняли и отклонили из прошлого отчёта |
| `docs/decisions.md` | бюджет ≤400 токенов и правило «ровно один playbook» |
| `docs/architecture.md` | куда playbook встраивается в контур |

**Промпт.**

```text
Задача: превратить найденные ранее источники в четыре готовых к вставке playbook'а
для системного промпта нашего агента и собрать к ним лицензионные notices.

Контекст. Агент работает на малой локальной модели офлайн, механику Claude Skills он
исполнять не умеет. Из чужих SKILL.md мы берём только содержание — порядок действий.
В промпт попадает ровно один playbook, выбранный после классификации задачи. Жёсткий
бюджет: не более 400 токенов на playbook, считая по токенизатору семейства GPT/LLaMA;
меньше — лучше. Playbook читает малая модель, поэтому это императивные короткие
шаги, а не эссе и не список CWE.

Четыре playbook'а.

1. code-audit: поиск уязвимости в исходниках, в первую очередь инъекции,
   аутентификация, работа с секретами. Порядок: карта источников и стоков → отбор
   файлов → чтение контекста → доказательство эксплуатируемости → отчёт.
2. code-fix: минимальное безопасное исправление security-дефекта в SWE-bench-подобном
   формате. Порядок: воспроизвести → локализовать → починить первопричину →
   перепроверить. Явный запрет ослаблять или править тесты и подгонять ответ.
3. forensics: разбор логов и артефактов инцидента. Порядок: инвентаризация
   доступных артефактов → нормализация времени → таймлайн → корреляция → IOC →
   вывод с уровнем уверенности. Не предполагать наличие journalctl, auditd, ausearch —
   сначала проверять, что реально есть.
4. ctf: локальный сервис или бинарь. Порядок: инвентаризация → поверхность атаки →
   дешёвые гипотезы вперёд дорогих → подтверждение флага/эффекта → фиксация.

Требования к каждому playbook'у.

- 15–30 строк, императив, второе лицо, без вводных и без похвалы;
- каждый шаг заканчивается наблюдаемым результатом, а не намерением;
- обязательный шаг внешней проверки перед завершением;
- явное правило остановки: когда бросать гипотезу и переходить к следующей;
- никаких имён конкретных задач, путей и флагов из чьих-либо примеров;
- посчитанное число токенов указать под каждым текстом.

Дополнительно.

- Для каждого playbook'а перечислить источники, из которых взято содержание, с
  лицензией и ссылкой на конкретный файл.
- Собрать готовый фрагмент THIRD_PARTY_NOTICES.md: по каждому источнику —
  название, ссылка, лицензия, дословный copyright notice, что именно заимствовано
  (идея/порядок шагов/формулировка).
- Отдельно отметить источники, откуда брать текст нельзя: лицензия отсутствует,
  запрещает производные работы или коммерческое использование.

Формат ответа. По одному разделу на playbook: текст в блоке кода, под ним число
токенов, под ним источники. В конце — фрагмент THIRD_PARTY_NOTICES.md целиком и
таблица «источник | лицензия | можно ли заимствовать текст».

Правила достоверности. Лицензию проверять на текущий момент по файлу LICENSE в
репозитории, а не по чужому пересказу. Дословные цитаты помечать как цитаты. Если
для playbook'а хорошего источника нет — писать его с нуля и честно указывать, что
источника нет.
```

**Приёмка.** Четыре текста, каждый ≤400 токенов по указанному токенизатору, и
notices, которые можно закоммитить без правок.

**Куда положить.** `docs/research/playbooks-draft.md`, notices — в корневой
`THIRD_PARTY_NOTICES.md` после нашей проверки лицензий.

## M8. Экономия токенов в agent loop

**Зачем.** Токены — второй критерий ранжирования. При равенстве решённых задач
выигрывает тот, кто потратил меньше. Но резать наугад нельзя: `docs/decisions.md`
требует сначала accuracy, потом compression, и только через абляции.

**Закрывает.** Шлюз E `PLAN.md`.

**Прикрепить.**

| Файл | Зачем |
|---|---|
| `docs/architecture.md` | где в контуре тратятся токены |
| `agent/limits.py` | текущие непроверенные лимиты, которые надо оспорить |
| `docs/decisions.md` | правило «один playbook ≤400 токенов» и запрет оптимизации без абляции |

**Промпт.**

```text
Задача: собрать приёмы сокращения токенов в цикле tool-using агента, у которых есть
измеренный эффект, и отделить их от фольклора.

Контекст. Наш агент — один цикл inspect → plan → act → observe → verify на малой
локальной модели. Резидентный контекст платится на каждом шаге: 30 шагов × 1,5k
токенов системного промпта — это до 45k input-токенов на одну задачу. Токены
считаются суммарно по всем 15 задачам и являются вторым критерием ранжирования после
числа решённых задач. Регрессия решаемости ради экономии токенов недопустима.

Что сделать.

1. Собрать приёмы сокращения input-токенов в агентных циклах: усечение вывода
   инструментов, суммаризация истории, скользящее окно, вынос статики из системного
   промпта, дедупликация повторяющихся наблюдений, ссылки на файлы вместо содержимого.
   Для каждого — опубликованные измерения эффекта, если они есть.
2. То же для output-токенов: ограничение рассуждений, структурированный вывод вместо
   свободного текста, запрет на пересказ наблюдений.
3. Найти опубликованные данные о том, какие из этих приёмов роняют качество и на
   каких задачах. Нам важнее всего: где усечение вывода инструмента приводит к потере
   критической информации и к неверному ответу.
4. Отдельно: что известно про кэширование промптов на локальных серверах инференса
   и учитывается ли кэшированный input как потраченные токены в типовых реализациях.
5. Прочитать приложенный limits.py и назвать значения, которые с точки зрения
   внешних данных выбраны неудачно, с обоснованием.

Формат ответа.

1. Таблица «приём | ожидаемая экономия | риск потери качества | как измерить у себя |
   источник».
2. Ранжированный список: что применять первым при нашем профиле нагрузки.
3. Список «не делать» — приёмы, которые чаще ломают решаемость, чем экономят.
4. План абляций: какие пять экспериментов ставить, чтобы проверить пункты 2 и 3,
   меняя ровно один фактор за раз.

Правила достоверности. Приём без измеренного эффекта помечай как непроверенный.
Не выдумывай проценты экономии. Не предлагай оптимизаций, требующих внешних сервисов
или сети.
```

**Приёмка.** Есть план абляций, каждая с одним изменяемым фактором и метрикой.

## M10. Грабли упаковки zip и preflight

**Зачем.** Ошибка формата архива обнуляет все 15 задач и при этом проверяется
детерминированно. Мы собираем zip на Windows — набор специфических граблей
(права, CRLF в shebang, пути, символические ссылки) здесь максимальный.

**Закрывает.** Шлюз A `PLAN.md`, задачу preflight, поднятую решением от 2026-08-25.

**Прикрепить.**

| Файл | Зачем |
|---|---|
| `docs/task.md` | требования к архиву: ≤10 МБ, run.sh в корне, исполняемость |
| `scripts/build_submission.py` | что уже собирается и чего в проверке не хватает |

**Промпт.**

```text
Задача: составить исчерпывающий чеклист причин, по которым zip-архив с агентом
не запустится в Linux-контейнере, и превратить его в скрипт проверки.

Контекст. Мы собираем архив на Windows, а запускается он в Linux-контейнере под
управлением стороннего runner'а. В корне архива должен лежать исполняемый run.sh,
который вызывается как ./run.sh "<текст задачи>". Размер — не более 10 МБ. Интернета
при запуске нет, зависимостей ставить нельзя. Одна ошибка упаковки обнуляет весь
результат, поэтому проверка должна быть параноидальной и детерминированной.

Что сделать.

1. Перечислить все известные причины, по которым такой архив ломается. Как минимум
   разобрать: бит исполняемости в zip, созданном на Windows; CRLF в shebang; BOM в
   начале скрипта; обратные слеши в путях; символические ссылки; жёсткие ссылки;
   пустые каталоги; имена в не-UTF8 кодировке; регистрозависимость имён; вложенный
   верхний каталог; скрытые файлы .git, .venv, __pycache__, .pytest_cache; файлы
   больше лимита; zip64; нулевая длина; неверная кодировка имён файлов внутри zip.
   Для каждой — как проявляется при запуске и как обнаружить до отправки.
2. Разобрать, чем отличается zip, созданный разными инструментами (python zipfile,
   Compress-Archive в PowerShell, 7-Zip, встроенный проводник Windows, zip в Linux),
   в части прав доступа и внешних атрибутов. Указать, какой способ сохраняет режим
   исполняемости и как это делается через python zipfile.
3. Написать скрипт проверки на python stdlib, который принимает путь к собранному
   zip и:
   - проверяет размер и целостность;
   - распаковывает во временный каталог;
   - проверяет структуру корня и наличие исполняемого run.sh;
   - проверяет shebang, окончания строк и кодировку;
   - ищет мусор: кэши, окружения, логи, ключи, .git;
   - ищет признаки сетевых вызовов и установки зависимостей в исходниках;
   - печатает SHA-256 и вердикт PASS/FAIL с перечнем причин.
   Скрипт должен работать и на Windows, и на Linux, без внешних зависимостей.
4. Отдельно перечислить проверки, которые невозможно сделать без запуска в целевом
   контейнере, — чтобы мы не считали preflight достаточным.

Формат ответа. Таблица причин отказа, затем скрипт целиком в блоке кода, затем
список проверок, требующих контейнера.

Правила достоверности. Поведение zip описывать по спецификации формата и по
документации инструментов, со ссылками. Скрипт должен быть работоспособен как есть,
без псевдокода и без TODO.
```

**Приёмка.** Скрипт запускается у нас на реальном архиве и ловит подложенные дефекты
(снятый бит исполняемости, CRLF, вложенный каталог) — проверяем намеренной порчей.

**Куда положить.** `docs/research/packaging-pitfalls.md`, код — как основа
`scripts/check_submission.py`.
