## Формула победы

Порядок шлюзов нельзя менять:

| Шлюз | Что может обнулить результат | Чем закрывается |
|---|---|---|
| A. Запуск | нет/не executable `run.sh`, ошибка импорта, неверный архив | contract test и smoke из распакованного zip |
| B. Среда | интернет/установка пакетов, несовместимость с образом | offline clean-container gate |
| C. Решаемость | неверный артефакт, timeout, непроверенный ответ | tool loop + внешний verifier + failure taxonomy |
| D. Обобщение | overfit на 6 public tasks | capability-oriented design, мутации и новые локальные fixtures |
| E. Эффективность | лишние prompt/tool tokens и wall time | абляции только после сохранения solved count |

Главная метрика — `solved_count`. Вторичные — `total_tokens`, затем `wall_time`.
Public score всегда подписывать как `x/6 public tasks`, а не как ожидаемые `x/15`.

## Выбранная архитектурная ставка

Аудит пяти вариантов (`docs/strategy-audit.md`) выбрал hybrid cascade:
детерминированный preflight/budget controller, один универсальный агент и внешний
verifier с одним recovery pass.

```text
instruction + deterministic preflight
        ↓
compact environment brief → task/capability hypothesis
        ↓
plan next action → local tool → observe compact result
        ↑                         ↓
        └──── recover/replan ← verify
                                  ↓
                               finish
```

Не делаем четыре независимых «агента по типам задач» до данных. Малой LLM нужен
общий надёжный контур, а специализацию сначала задают prompt playbooks и компактный
ACI. Направление принято, но параметры budget/tool protocol остаются гипотезами до
baseline. Архитектура — `docs/architecture.md`, мелкий порядок работ —
`docs/plans/PLAN-KT4.md`.

## AFK-очередь 26.08.2026, вечер → ночь (сессия на Linux-машине с ollama)

Контекст, которого не было у прошлых сессий: эта машина — Linux (не Windows/WSL),
на ней работает Docker 29.6.2, целевой образ `secureintelligent/acp` скачан по
digest `sha256:1324d7bb…`, и главное — есть **живой локальный endpoint**: `ollama`
с четырьмя 7B-моделями класса qwen2.5-coder (`tools`-capable). То есть шлюз C
(решаемость) впервые можно измерить, а не оценить.

Первое измерение уже сделано и меняет одно из допущений кода: против
`qwen2.5-coder:7b` ступень `native_tools` **проваливается** (модель возвращает
объект без обязательного ключа), а `json_schema`, `json_object` и `text` проходят.
`limits.DEFAULT_CALL_STYLE = "native_tools"` обоснован конфигурацией эталонного
агента организаторов и по-прежнему может быть верен для их endpoint — но это больше
не единственное наблюдение, и лестница fallback перестала быть страховкой «на всякий
случай».

Уточнено 04.09: модель возвращает не «объект без обязательного ключа», а конверт
`{"name": <инструмент>, "arguments": {...}}` в `content` — форму функции с именем
инструмента вместо имени предложенной функции. Это происходит в 36 прогонах задач из
36, то есть ступень стоила каждой задаче лишнего запроса. Чинится приёмом ответа
(`agent.llm._unwrap_function_envelope`), а не сменой ступени: `LADDER` движется только
вниз, и старт ступенью ниже сделал бы `native_tools` недостижимой на endpoint, где
работает только она.

Порядок задач ниже — это порядок шлюзов из «Формулы победы», менять его нельзя:
сначала решаемость, потом токены, потом время.

- [x] **L1. Стенд живого прогона.** `scripts/eval/` — прогон собранного архива против
      одного task package: контейнер из `environment/Dockerfile`, endpoint пробрасывается
      с хоста, после агента запускается `tests/test.sh`, результат читается из
      `/logs/verifier/reward.txt`. Одна строка метрик на задачу: reward, tokens, wall,
